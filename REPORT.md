## 1. What this report covers

The original proposal lays out a 10-week plan (data & baselines → knowledge base & Fusion RAG → agentic orchestration → UI → evaluation). At the user's request, this implementation pass **ignored the week-by-week schedule and built a complete, working, end-to-end version of every deliverable in one continuous session**, rather than staging it across weeks. This document reports what was actually built, how it maps onto the proposal's methodology and deliverables sections, what evaluation results it produced, and — importantly — where the implementation had to substitute a lighter-weight component for something the proposal named (e.g. Prophet, live Neo4j, a downloaded transformer encoder) and why, so the deviations are explicit rather than silent.

All claims below are backed by code in this repository and a passing automated test suite (`roamwise/tests/test_pipeline.py`, 157 passing and 1 skipped — the skip is the local-LLM path, which needs an optional dependency).

## 3. Methodology → implementation mapping

### 3.1 Data sourcing

The proposal names Kaggle, TripAdvisor, OpenStreetMap, and Wikidata. Every dataset the app ships is derived from those sources by `roamwise/pipeline/`, which reads its city list from `common.CITIES` — with one source the proposal does not name and §5 states plainly: 180 rows' opening hours and 60 rows' price tier come from Google Maps (`pipeline/enrich_gmaps.py`, issue #71), and `hours_source`/`price_source` name it row by row. `roamwise/data/generate_data.py` produced the earlier synthetic versions and is retained only for `user_survey.csv`:

- **2 cities — Paris and Berlin**, each with a budget tier and interest tags, emitted from the registry by `build_destinations.py` (which also validates the tags against the 13-word vocabulary `agents/orchestrator.py` maps onto traveller preferences, since a tag outside it is silently dropped rather than raising)
- **18 transport hubs** (10 Paris, 8 Berlin), found in OpenStreetMap and ranked by Wikidata sitelink count rather than hand-picked. The previous two-per-city set was wrong at both ends: CDG sits 23 km outside the catalogue, so its 3 km circle was empty, while "all stations" would have put 365 rows in Paris alone and made proximity meaningless
- **2 city guides**, derived from the catalogue by `city_guide.py` (cluster structure, walkability, observed closing hours) plus one hand-written editorial sentence per city, kept separate so its provenance is visible. They form part of the semantic/keyword corpus

**Why two cities rather than eight.** The previous catalogue held 150 POIs per city; this one holds 371 and 283. Per-city depth is what the retrieval comparison and the itinerary optimiser actually exercise, and coverage against an independent Wikivoyage reference list roughly doubled as a result — Paris 38% → 74.4%, Berlin to 67.2%, measured with one-to-one matching so a single catalogue entry cannot claim several reference entries. §5 records what the narrower list costs.

Those coverage figures survived the removal of 46 rows that were not places to visit (issue #65), which is itself the cleanest evidence that they were not: Paris held 186/250 of the reference list before and after, Berlin 156/232, while the share of the catalogue that *is* on the reference list rose from 46.5% to 50.1% in Paris and 52.0% to 55.1% in Berlin. Dropping universities, metro stations and a television channel cost no coverage and bought precision, because Wikivoyage never listed them either.
- A 420-row synthetic user-preference survey across 7 named traveler archetypes, used to fit the segmentation model

POIs and tourism-demand data are now **real**, fetched live from public APIs rather than generated:

- **`pipeline/build_catalogue.py`**: **654 POIs** — 371 Paris, 283 Berlin — pulled from **Wikidata** (SPARQL, via the QLever endpoint), cross-matched against **OpenStreetMap** (Overpass) within ~7 km of each city centre and enriched from **Wikipedia**: the sources the proposal names for this exact purpose. (The earlier `data/fetch_real_pois.py` produced the eight-city, 1200-row version and is superseded; it is kept only for history.)

  **Which** POIs turns out to matter as much as how many. The first version of this pipeline ranked candidates only by whether they carried a `wikidata` tag and then took Overpass's arbitrary return order, so each city's catalogue was effectively a random sample of its tagged features — Paris's contained neither the Louvre, the Musée d'Orsay nor the Arc de Triomphe. Selection now ranks within each category by a fame score blending Wikidata sitelink count with Wikipedia pageviews, weights fitted against an independent Wikivoyage reference list. On the eight-city catalogue where this was first measured, coverage of 47 headline sights went from **20/47 to 42/47** at the same catalogue size; on the two-city one it is the 74.4% / 67.2% reported in §3.1 above.

  Two further corrections come from the same work, and both still apply. OSM's `wikidata` tag is hand-applied and often points at a *concept* rather than the feature — a statue of Diana carries the QID for the goddess, the metre marker in Paris the QID for the unit of length. Because a concept article collects far more sitelinks than any building, these outranked real landmarks. Entities whose English Wikipedia article carries no coordinates are therefore rejected as non-places. And `popularity_score`, once derived from sitelink count alone, compressed the whole catalogue into eight distinct values between 4.0 and 4.7; it is now a within-city percentile of sitelink count blended with mean monthly English-Wikipedia pageviews.

  Descriptions are the opening sentences of the Wikipedia article where one exists (**593** of 654), the Wikidata one-liner where it does not (**13**), and a category template only as a last resort (**48**) — previously every description was templated. Each row carries provenance columns (`wikidata_qid`, `wikipedia_title`, `sitelink_count`, `monthly_pageviews`, `description_source`, `hours_source`, `price_source`) so any consumer can tell an observed value from a fallback — and, since issue #71, which *observed* source a value came from. `hours_source` reads `osm` for **197** of 654 rows, `gmaps` for **180** and `category_default` for **277**; `price_source` reads `osm` for **80**, `gmaps` for **60** and `category_default` for **514**. So **59.9%** of opening windows are observed rather than assumed, against 39.8% before that issue. What the remaining coverage costs the itinerary, and what taking the Google source cost, are both measured in §5.
- **`pipeline/build_demand.py`**: the monthly tourism-demand series is Eurostat's `tour_occ_nin2m` — real nights-spent data at **NUTS 2 region** granularity. Berlin *is* a NUTS 2 region (DE30), so its series is the city itself; Paris maps to Île-de-France (FR10), wider than the city but far tighter than France. This replaced the country-level `tour_occ_nim` proxy that `data/fetch_real_demand.py` used, and the difference is not cosmetic: the forecaster consumes seasonal *shape*, and the national series changed the crowding label in 8 of 12 Paris months. What remains — nights spent rather than arrivals, and uneven publication lag between the two regions — is documented in §5 below.

Every one of these files is committed, so the app runs from a fresh clone with no network access and no generation step. `generate_data.py` is retained only as the source of record for `user_survey.csv`, which no pipeline script reproduces; running it also rewrites the other four files with the superseded eight-city set, so it is not part of setup.

### 3.2 Predictive & segmentation models ("The Tools")

- **Demand forecasting** (`models/forecasting.py`): the proposal suggests Prophet or LSTM. This implementation uses **Holt-Winters triple exponential smoothing** (`statsmodels.tsa.holtwinters.ExponentialSmoothing`, additive trend+seasonality, damped trend) instead. Rationale: it needs no compiled Stan backend (Prophet's dependency) or GPU/training-data volume (LSTM), trains in milliseconds on 90 monthly points per city, and is fully sufficient for a 12-month-ahead forecast at this data volume. Forecast output is converted into a `low`/`medium`/`high` crowding label (z-score against each city's own post-pandemic history) — this is what the rest of the system actually consumes, not raw visitor counts. `models/forecasting_prophet.py` is an optional Prophet-based alternative with the same output shape, added to empirically test that rationale rather than just assert it — see the backtest below.

#### Holt-Winters vs. Prophet backtest (issue #3)

`evaluation/forecasting_comparison.py` holds out the last 6 months of each city's real Eurostat demand series, fits both models on everything before that, and scores each forecast against the real held-out values:

| Model | Mean MAE | Mean RMSE |
|---|---|---|
| **Holt-Winters** (default) | **107,846** | **130,424** |
| Prophet | 270,198 | 280,327 |

Per city: Holt-Winters MAE 95,571 (Berlin) and 120,121 (Paris); Prophet 213,650 and 326,745.

(Full per-city results: `evaluation/forecasting_comparison_results.csv`; aggregated: `evaluation/forecasting_comparison_summary.csv`. Reproduce with `pip install -r requirements-prophet.txt && python evaluation/forecasting_comparison.py`.)

**Reading this honestly:** Holt-Winters now wins on **both** cities rather than on the mean alone, and by a factor of roughly 2.5. That is a cleaner result than the previous revision's — which had Prophet ahead on 5 of 8 cities, with the aggregate swung by one volatile city (Rome) — but it is a *different measurement*, not a refutation of that one: different cities, and a regional rather than national series. The absolute error figures dropped by an order of magnitude for the same reason, because regional nights-spent counts are simply smaller numbers than national ones; only the ratio between models is comparable across revisions.

The gap should be read alongside how little history each city has. Post-2022-07, Paris has 42 monthly points and Berlin 30, and the backtest holds out the last 6 of them — Prophet emits an under-identification warning on Berlin for exactly this reason ("yearly seasonality enabled with less than 730 days of history"). Prophet's piecewise-linear trend detector needs more data than that before its flexibility pays for itself, while Holt-Winters' damped trend degrades gracefully. So the finding supports the original engineering trade-off empirically rather than by assertion — Holt-Winters is the right default *at this data volume* — and it says nothing about which model would win with a decade of history.

- **Traveler segmentation** (`models/segmentation.py::TravelerSegmenter`): KMeans (k=7) over 6 preference dimensions (budget, culture, nature, nightlife, relax, adventure), fit on the synthetic survey, with each cluster mapped to its majority-vote archetype name for interpretability. The model still takes six features; the UI asks for five and supplies the survey mean for `adventure`, for the reason given in §5.
- **POI geographic zoning** (`pipeline/city_guide.py`): the proposal's second, independent KMeans, clustering a city's POIs by lat/lon into geographic areas. It now serves the **city guides** — the derived guide text describes each city area by area, so retrieval returns the same spatial structure a traveller reads a city in.
  - *Historical note (issues #19, #72, #81).* This clustering used to sit on the router's path as `models/segmentation.py::POIZoner`, which cut a city's candidate POIs into `n_days` walkable zones — one zone per itinerary day. Because plain KMeans optimizes only for geographic compactness, it collapsed the dense historic centre into one oversized zone and left outlying sights in zones of one, producing trips with a six-stop day beside three near-empty ones; issue #19 replaced nearest-centroid assignment with a cheapest-pair-first pass under a `ceil(n / n_days)` cap plus a repair pass that refused to leave a zone empty. Issue #72 then made day assignment a decision the TOPTW model takes jointly with selection and ordering (see `RouterAgent` below), which is strictly better — the optimiser weighs which day a stop belongs to against what else fits that day, rather than inheriting a partition fixed before any scheduling is known. That left `POIZoner` called by nothing but its own tests, and issue #81 removed it; the guarantee its tests carried (a trip returns every day it asked for, even when the sightseeing pool is empty) is now asserted end to end against the router.

### 3.3 Fusion RAG architecture (core retrieval layer)

Implemented exactly as three components fused by reciprocal rank fusion, per the proposal:

- **Semantic search** (`retrieval/semantic_search.py`): the proposal names FAISS/ChromaDB over transformer embeddings. This now uses exactly that: **`sentence-transformers` (`all-MiniLM-L6-v2`) embeddings indexed in FAISS** (`IndexFlatIP` over L2-normalized vectors, i.e. exact cosine-similarity search) -- see issue #4. The project originally shipped a TF-IDF+LSA stand-in instead (no multi-hundred-MB model download, sub-second fit time); that trade-off is now paid (`SemanticIndex.__init__` takes ~9s to load the model and encode the 654-POI + 2-guide corpus, vs. milliseconds before) in exchange for genuine semantic embeddings rather than a keyword-co-occurrence proxy for them. `SemanticIndex`'s public interface (constructor + `.search(query, top_k, destination_id)`) is unchanged, so `retrieval/fusion.py` and everything upstream of it needed zero changes.
- **Graph-RAG** (`retrieval/graph_search.py` + `knowledge_graph/build_graph.py`): the proposal names Neo4j or NetworkX; this implementation uses **NetworkX** (a `MultiDiGraph`), which needs no server process and is fully unit-testable. `GraphIndex` exposes genuine multi-hop traversal — `multi_hop_transport_to_poi()` walks `City -[HAS_TRANSPORT]-> Transport -[SERVES]-> POI` and ranks by journey time to the nearest hub, which is exactly the kind of chained relational query the proposal argues flat document retrieval cannot answer. Those minutes are solved over the cities' GTFS timetables (`data/street_network/{CITY}_transit.npz`), so the relation states something no POI's own document does. Until issue #126 it did not: the traversal fetched two one-hop sets and computed a haversine cross-product in Python over an edge the graph never held, and the two relations that *were* stored — `NEAR` and `SAME_CATEGORY`, 97% of the graph's 95,845 edges — had no consumers at all. Rebuilding it on real transit edges took "museums near a Paris transport hub" from 6 answers to 36, the Louvre among them: over a kilometre from any mainline station, twelve minutes from Saint-Lazare. On top of those edges sits the chain the proposal calls *sequencing constraint-aware*: `anchor -[SERVES ≤15min]-> POI_a -[REACHABLE ≤10min]-> POI_b`, valid only where **POI_b is still open once POI_a closes**. The anchor is the gateway the traveler named, or the city centre — where the router already starts every day but the first. Both POIs come back as ordinary retrieved documents carrying the path they came from (`Paris →3.0min→ Bazar de l'Hôtel de Ville (closes 20:00) →9.3min→ Notre-Dame de Paris`), which is what makes provenance in the "What the plan was grounded in" block a route the reader can follow rather than an assertion. It shipped behind `ROAMWISE_GRAPH_CHAIN` **off by default**, precisely because the anchor is not keyword-triggered and the chain therefore moves every plan; #126 Phase 5 opened the flag once the full 12/15/18-hour grid showed nothing regressing, so it is **on by default now** and the flag still works in both directions (`ROAMWISE_GRAPH_CHAIN=0`), which is what keeps that comparison reproducible. What that gate establishes, and what it does not, is stated in §5. `GraphSearchIndex` routes a natural-language query to the right traversal (archetype-preference edges, category filters, transport-proximity) via lightweight keyword matching.
- **Keyword search** (`retrieval/keyword_search.py`): BM25 via `rank_bm25`, as specified.
- **Fusion**: reciprocal rank fusion (`retrieval/fusion.py`), the proposal's named alternative to a learned re-ranker (chosen because it needs no training data). `FusionRetriever.retrieve(query, config=...)` exposes all three comparative-analysis configurations (`fusion`, `hybrid`, `standard`) from a single object.

### 3.4 Agentic orchestration (core focus)

The proposal names LangGraph "or similar multi-agent systems." This implementation is a **lightweight custom state-machine orchestrator** (`agents/orchestrator.py::RoamWiseOrchestrator`) rather than LangGraph itself — a deliberate choice to keep the dependency surface minimal and the control flow fully deterministic and inspectable for grading, while preserving the same shape LangGraph would enforce (a shared state dict threaded through named agent nodes). Three specialized agents, as specified:

- **`ForecasterAgent`** — interprets the Holt-Winters output into a crowding narrative and low-crowding-month recommendations.
- **`FusionRAGAgent`** — orchestrates the three-component retrieval pipeline and grounds its narrative *only* in retrieved snippets.
- **`RouterAgent`** — does not ask the language layer to invent a route; it makes two decisions in order and narrates the result. First it **scores** every candidate against the traveller's own six sliders (`optimization/scoring.py`) and keeps the best of them; then it hands those to a **TOPTW solver** (`optimization/toptw.py`, OR-Tools) which decides which stops actually fit, on which day, in which order and at what hour. This is the proposal's "optimization methodology as a tool" requirement, and issue #72 is what made it a single optimisation rather than a TSP followed by six repair passes. The split between the two is measured, not assumed: scoring the *candidates* beat selecting them by archetype-driven retrieval at equal candidate count (more stops a day at the same distance per stop, better-known places, more categories a day), while additionally weighting the *solver* with the same scores cost stops and distance and moved preference match by 0.614 → 0.639 — its own objective, not an independent judge. The preference signal is therefore spent once, at selection. See `evaluation/toptw_scoring_ablation.py`. The tool can use either haversine straight-line distance priced at the selected travel mode's speed (default), or real street-network distances/times (`use_real_routing=True`), measured along OpenStreetMap's own footpath and road networks. Those distances used to come from a public OSRM demo server; issue #32 moved them into the repo, so they are now computed offline from committed data (`optimization/street_network.py`, §5). Either way the tool always respects each POI's opening hours: a stop the router would reach before it opens gets a wait folded into the day's elapsed time, and a stop already closed for the day is skipped rather than scheduled anyway.

  **Travel modes** (`optimization/travel_modes.py`, issue #19): legs are costed as `walking` (4.5km/h, measured on the pedestrian network), `driving` (25km/h urban door-to-door plus an 8-minute parking overhead, measured on the road network), `transit` (journey times solved from the city's own GTFS timetable, where one ships — see §5), or `hybrid`. Hybrid is not an averaged speed — it is decided per leg, walking anything within 1.2km and driving the longer hops between neighbourhoods, which is how people actually move around a city and which an averaged speed gets wrong in both directions. With real routing on, hybrid reads both the foot and car matrices so the choice is made on true street distances.

  **The model** (`optimization/toptw.py`, issue #72): days are vehicles on one absolute clock, each POI gets a copy per day carrying that day's opening window, and every stop is optional — a disjunction whose penalty is what skipping it costs. Meals, evening venues, day filling, day balancing, the nightlife hour floor and the nightlife-last reorder were six separate passes before; they are constraints of this one model now. That mattered because the passes ran over each other's output against the same budget with no view of one another: raising `min_food_per_day` from 0 to 2 *removed* a nightlife stop, and the two-meal guarantee held on only 28 of 72 measured days, falling to 4 of 24 on eighteen-hour days — the longer the day, the more passes competed over it.

  **Meals** are one sitting per day per mealtime, not a count: a bare "two food stops a day" is satisfied by two lunches at 11:00 and 11:45, so each sitting is a copy with its own time window, aimed at a fraction of the day's window and then pulled back into hours a kitchen is actually open. The band is load-bearing — a Nightlife Seeker's day starts at 15:00, and on an eighteen-hour day the fractions alone put the second sitting at 06:18, an hour with no restaurant open anywhere in the catalogue. Meals now hold on **72 of 72** days.

  **Diversity** is a per-day cap on stops of one category (4, food exempt). It cannot be a term in the score, as issue #72's formula proposes: "the third museum today" is a property of a partial route, not of a POI, so it has no value at the time a static node weight is set. As a category quota it is exactly what a constraint model can express and a chain of passes cannot. 4 was swept: on a 72-POI pool it is the distance-per-stop optimum (0.471 km, against 0.536 at 3 and 0.481 at 5), and on the 24-POI pool the app retrieves today it still beats the old router on stops (+7.8%) where a cap of 3 does not (−2.0%). The cost is visible and worth stating: at 4, about two-thirds of days contain four stops of one category, where a cap of 3 leaves none.

  **Measured against the previous router** over the same 72 days (2 cities × 4 archetypes × {12,15,18}h × 3 days, same candidates, same geography, haversine, walking):

  | retrieved pool | | stops/day | km/stop | days with both meals |
  |---|---|---|---|---|
  | 24 (the old default) | previous | 6.21 | 1.582 | 28/72 |
  | | TOPTW | **6.69** (+7.8%) | **0.906** (−42.7%) | **72/72** |
  | 72 (**the default now**) | previous | 7.82 | 1.054 | 42/72 |
  | | TOPTW | **9.06** (+15.8%) | **0.471** (−55.3%) | **72/72** |

  Zero stops scheduled at a closed venue and zero budget overruns in every cell. The gain is not a trade: issue #72 had measured that a greedy time-windowed insertion buys +6% stops at +12% km per stop, and left open whether a real solver could take the stops without the distance. It can — both improve at once, and the greedy penalty was an artefact of greediness rather than an inherent cost. Determinism is a fixed iteration budget rather than a wall-clock limit, so the same input returns the same itinerary on any machine; verified over repeated solves.

  **Pool size and latency.** `RETRIEVED_POIS_PER_DAY` went from 8 to 24 (issue #72), which is what makes the lower row above the shipped configuration rather than a hypothetical: selection used to be retrieval's job because the router could not do it, and now that the score and the solver choose from the pool, a wider pool is something to choose *from*. It is not free. Node count is candidates × days, so a longer trip pays twice, and at 24/day a five-day plan took 29s and a four-day one 33s.

  The cause was not the pool, which is the useful part. Measured across pool sizes at fixed trip length, solve time barely moved — four days took 16.4s at 258 nodes and 15.6s at 610 — while it climbed steeply with *days*. That pointed at `use_extended_swap_active`, a local-search operator enabled here to fix a balance problem: because each POI is a per-day copy, moving one between days means deactivating one node and activating another, and no default operator makes that move, so `[4, 0]` stayed `[4, 0]`. On a real pool the operator is pure cost — three days 3.0s → 16.2s while *losing* a stop (9.00 → 8.67 per day), four days 4.2s → 18.2s for a byte-identical itinerary, five days 5.9s → 61.4s. It is now enabled only when the pool is too small to fill the trip, where it is both needed and cheap. Worst observed plan across 1–5 days, two cities and two archetypes: **9.6s, down from 33.0s**, with the small-pool behaviour intact.

  Three bugs are worth recording because each looked like a modelling failure and was not. A meal-shortfall penalty set far above the rest of the objective (10,000,000) made guided local search return an **empty trip** — one term dwarfing every gradient it could follow; it is proportional to the drop penalty now. `PATH_CHEAPEST_ARC` builds routes one vehicle at a time and dead-ends when each vehicle carries its own quotas, returning `[0, 0, 7]` stops across three days where parallel insertion returns `[6, 7, 6]` on the same input — raising the iteration limit sevenfold changed nothing. And OR-Tools treats an empty vehicle as *unused*, dropping its soft cumul penalties from the objective entirely, so every per-day floor was silently inactive on exactly the days that needed it.

The orchestrator's `plan_trip()` runs all five nodes in sequence: segmentation → destination selection (forecaster used as a scorer across every city in the catalogue — two, since §3.1 — combining tag affinity, budget fit, and crowding penalty) → Fusion RAG retrieval → routing → final synthesis.

**Reasoning-engine note:** every agent's natural-language synthesis step goes through a pluggable `LLMClient` (`agents/llm_client.py`). The default, zero-cost `TemplateLLMClient` composes retrieved facts into readable prose deterministically, so the entire pipeline — including the Streamlit app — runs fully offline with no API key and no per-run cost. If the user sets `ANTHROPIC_API_KEY` and installs the `anthropic` package, every agent automatically switches to live Claude narration with no code changes. A third option (`LocalHuggingFaceLLMClient`, issue #54) runs a small open-weight model (Qwen3-4B-Instruct, Apache-2.0, 4-bit via MLX) entirely on-device — no API key, no per-run cost, no network dependency beyond the one-time model download — activated by setting `ROAMWISE_LOCAL_LLM=1` after installing `requirements-local-llm.txt`; see §3.4.2 for a worked example. All three paths share the same interface, so which one runs never changes any other agent's code. This was a deliberate safety/cost decision: the system never assumes network access or spends the user's API budget without explicit opt-in.

#### 3.4.1 Custom orchestrator vs. LangGraph — a direct comparison

`agents/orchestrator_langgraph.py` reimplements the exact same five-node flow on `langgraph.graph.StateGraph`, reusing the same underlying agent classes (`TravelerSegmenter`, `ForecasterAgent`, `FusionRAGAgent`, `RouterAgent`) so only the orchestration layer itself differs. `RoamWiseLangGraphOrchestrator.plan_trip()` has the identical signature and return shape as `RoamWiseOrchestrator.plan_trip()`. That sentence used to cite `test_langgraph_orchestrator_matches_custom_orchestrator_interface` as its verification, and the citation was doing less work than it looked: that test asserts the *return shape*, so a parameter present on one orchestrator and absent from the other passes it. One was — `start_date` reached the router on the hand-rolled path and not on the LangGraph one, which meant the verbatim OSM opening-hours tag had no weekday to resolve against there and fell back to the coarse open/close pair: `Tu-Su 10:00-18:00; Mo off` read as open on a Monday. Measured over the 654-POI catalogue by resolving each tag against all seven weekdays and comparing that with the coarse pair the router falls back to when it has no date: 342 POIs (52.3%) resolve to a different window on at least one weekday, and 153 (23.4%) read as open on a day they are in fact shut — Monday worst by a wide margin at 101, then Sunday at 46. Issue #76 closed it, and what guards the pair now is behavioural: `test_both_orchestrators_honour_the_weekday_a_start_date_names` plans the same Monday trip through both orchestrators and asserts neither schedules a stop outside that weekday's hours, while `test_a_start_date_also_reaches_the_forecaster_on_the_langgraph_path` covers the same date's other consumer — a start date supersedes `travel_month`, so omitting the derivation forecasts crowding for the wrong month. Both are skipped only where the optional `requirements-langgraph.txt` extra is absent; CI installs it, so the GitHub Actions run exercises both orchestrators on every push.

| | Custom state machine (`orchestrator.py`) | LangGraph (`orchestrator_langgraph.py`) |
|---|---|---|
| Dependency weight | None beyond the project's existing deps | Pulls in `langchain-core`, `pydantic`, `langgraph-checkpoint/-prebuilt/-sdk`, `xxhash` |
| Conditional branching (skip destination-selection when the user pins a city) | A plain `if destination_id is None:` inside `plan_trip()` | An explicit `add_conditional_edges("segment", ..., {...})` — declarative, and the branch is visible in the graph structure itself, not buried in a function body |
| Debuggability | Set a breakpoint anywhere in one linear method; the whole call stack is normal Python | Each node is a separate method invoked by the LangGraph runtime; tracing requires either LangGraph's own introspection (`.get_graph()`, LangSmith) or breakpoints inside each node individually |
| Extensibility toward real agent loops (retries, human-in-the-loop, parallel branches, checkpointed/resumable state) | Would require hand-building each of those | Native: checkpointers, conditional edges, and parallel fan-out are first-class primitives already installed as dependencies |
| Lines of orchestration-specific code | ~50 | ~95 (mostly `TypedDict` state schema + per-node method wrappers) |
| Verified behavior | Full test suite + Streamlit app | `plan_trip()` produces an identical result to the custom orchestrator on the same inputs (both deterministic under `TemplateLLMClient`); conditional edge verified to correctly skip `select_destination` when a city is pinned |

**Takeaway:** at this project's current scope — a fixed five-step pipeline with one conditional branch — the custom orchestrator is genuinely simpler with no behavioral downside, which is why it stayed the default. LangGraph's value only shows up once the orchestration needs something the custom version doesn't have: retries/backoff on a failing tool call, a human-approval step before booking, parallel exploration of multiple candidate destinations, or resumable/checkpointed runs across a multi-turn conversation. None of those are currently implemented in either orchestrator; if the project grows toward them, `orchestrator_langgraph.py` is the better foundation to extend.

#### 3.4.2 A live, non-template LLM run (issues #54, #56, #57)

The Anthropic path (§3.4, issue #7) needs a paid, provisioned API key that no build environment so far has had, which is why every prior report used the deterministic `TemplateLLMClient`. `LocalHuggingFaceLLMClient` closes that gap for free: `mlx-community/Qwen3-4B-Instruct-2507-4bit` (Qwen3, Apache-2.0, 4-bit quantized for Apple's MLX runtime — Apple Silicon only) runs entirely on-device, downloading once (~2.1GB) to the user's own Hugging Face cache rather than being bundled with the repo (see `requirements-local-llm.txt` for why committing the weights isn't practical: GitHub blocks any single file over 100MB outright, and recommends whole repos stay under 1–5GB).

Running it exposed two problems that the deterministic default had been hiding for the entire life of the project, both fixed in issues #56 and #57. A third of the same family surfaced later and is in §3.4.3 (issue #125): the narrative was being cut off at a fixed output cap, which offline could never happen because offline the prompt *is* the answer.

**The narrative recommended places that were not in the itinerary (#56).** `_synthesize()` used to hand the model two lists of places — the Fusion RAG *candidates* and the routed *itinerary* — with nothing saying which was the plan. Those are very different sets: retrieval returns candidates, and the router then drops most of them on opening hours, travel time and the day budget. On a measured 3-day Berlin plan, **4 of the 6** retrieved POIs pasted into that prompt were not in the itinerary at all, so the model blended both and sent the reader to stops the route never contained. Under `TemplateLLMClient` the prompt is echoed back verbatim, so no amount of offline testing could surface this: it is a prompt-design bug that only a real generative model can express. The fix removes the candidate list from the prompt entirely and moves each stop's description onto the stop itself (`RouterAgent._facts`), so the itinerary is the only list of places the narrator ever sees.

**A trip cost four generations, two of which nobody read (#57).** `plan_trip()` ran `ForecasterAgent._narrate`, `FusionRAGAgent._narrate`, `RouterAgent._narrate` and `_synthesize` in sequence. Only the first and last are rendered — `views/itinerary.py` reads `forecast["narrative"]` and `final_plan` and nothing else. The middle two existed solely to paraphrase structured data into prose that was then pasted into another model's prompt, which costs a full generation pass and paraphrases the same facts twice. Both agents now expose deterministic `facts` alongside their optional `narrate()`, and the orchestrator consumes `facts`.

The two fixes compound, because the second one also removes a stage of paraphrase drift feeding the first.

| | Before | After |
|---|---|---|
| LLM generations per trip | 4 | **2** (forecast + final plan — the two a user actually reads) |
| Berlin, 3-day, wall clock | **>400s** (measurement timed out) | **22.5s** |
| Paris, 3-day, wall clock | not measured (see above) | **48.1s** |
| Retrieved-but-unrouted places offered to the narrator | 17 candidates in-prompt | **0** — not in the prompt at all |

**Grounding check.** Over BER and PAR 3-day plans, all **11 of 11** routed stops are named in each narrative, and **0** places appear that the model was not shown. That last criterion needs stating precisely, because the obvious version of it is wrong: an off-route name appearing in the text is *not* by itself evidence of invention. The Humboldt Forum's own grounded description says it sits on Museum Island, so a narrative correctly describing that stop says "Museum Island" while recommending nothing off-route. The check that actually distinguishes a fault is whether a named place appears **nowhere in what the model was given** — `tests/test_pipeline.py::ungrounded_places` implements exactly that, and `test_synthesis_prompt_offers_no_place_outside_the_itinerary` enforces it per city under the template client, where the prompt *is* the output and no model download is needed.

What this does **not** fix is the subtler failure documented when #54 landed: the model still layers unverified elaboration on top of correctly-grounded stops (claimed exhibition contents, atmosphere descriptions). Nothing in the pipeline checks those, and the grounding criterion above deliberately does not claim to — it constrains *which places* appear, not *what is said about them*. The full raw output of a post-fix run is preserved in `evaluation/local_llm_sample_run.md`.

This remains a per-run structural check. The systematic measurement is `evaluation/hallucination.py` (§3.5), which grades generated narratives from all three retrieval configurations against the catalogue; it shares this exact definition of "the model was never shown this", so the per-run test and the systematic number cannot drift apart. `run_llm_hallucination_probe()` — the zero-context baseline — was written against `AnthropicLLMClient` and gated on `ANTHROPIC_API_KEY`, so choosing NVIDIA (#7) left it permanently skipped and it never once wrote its CSV; it goes through `get_default_llm_client()` now and refuses under the offline template rather than reporting a score no model produced (#132).

#### 3.4.3 The narrative stopped mid-sentence, and nothing said so (issue #125)

A third bug of the same family as #56 and #57 — invisible under `TemplateLLMClient`, obvious the moment a real model runs. A 3-day plan came back with a complete 3-day route and a narrative that described **two** days and stopped in the middle of a word.

**The output cap was a constant; the prompt is not.** Both clients passed a flat `max_tokens=1024`. The synthesis prompt grows with the trip — measured on the committed catalogue with the tokenizer the local model actually uses:

| Trip | Stops | Synthesis prompt (tokens) | Old cap |
|---|---|---|---|
| 3 days, 8h days | 22 | 1321 | 1024 |
| 5 days, 8h days | 35 | 2002 | 1024 |
| **3 days, 12h days** (the app's default) | **30** | **1799** | 1024 |
| **5 days, 12h days** | **45** | **2610** | 1024 |

At the app's own sidebar defaults the narrator was asked to describe 30 stops and given less room than the facts themselves occupied. The cap is now derived from the prompt (`llm_client.budget_for`) rather than fixed, so every call gets room proportional to what it was asked to describe.

**The clearest evidence is the same generation run twice.** Decoding is greedy, so the pre- and post-fix runs of a 5-day plan produce character-for-character identical text until the cap intervenes:

| | Narrative ends |
|---|---|
| Before | `…Enjoy the quiet beauty, the depth of` |
| After | `…Enjoy the quiet beauty, the depth of meaning, and the city's enduring spirit.` |

**Truncation is now reported rather than inferred.** Raising the cap alone would have left the same bug waiting at a longer trip. `Completion` carries a `truncated` flag — read from Anthropic's `stop_reason` and from the MLX stream's `finish_reason`, neither of which was previously looked at — which is logged as a WARNING to the System logs screen and surfaced in the UI instead of presenting half an itinerary as the whole one.

**#57's cost regression had come back by another route.** #57 removed the two paraphrases nobody reads, but its test pins `destination_id`, and the app does not: unpinned, `_recommend_destination` runs the forecaster over every city in the catalogue to read one field, and the forecaster narrated unconditionally. That is N+1 generations per request with N discarded — the flag #57 gave `FusionRAGAgent` and `RouterAgent` was never given to `ForecasterAgent`.

| Berlin, 3-day, 12h days, unpinned | Before | After |
|---|---|---|
| LLM generations per trip | 4 | **2** |
| Wall clock (M3 MacBook Air) | 136.4s | **82.9s** |
| Narrative covers every day of the route | 3/3 here, **but cut at 5 days** | **yes, 3/3 and 5/5** |

The 3-day figures are like-for-like — both runs produce the identical 3498-character narrative, so the saving is the two discarded generations. The 5-day pair is **not** comparable as a timing measurement (191.2s before, 269.4s after) precisely because the earlier run stopped early; it produces more text now because it is allowed to finish. All timings are from a fanless M3 MacBook Air where sustained generation throttles, and are not comparable to the figures in §3.4.2 above, which were taken on different hardware.

Whether a given 3-day plan trips the old cap is a boundary condition, not a certainty: a plan whose narrative lands just under 1024 tokens completes, and the same trip length with a start date set lands just over and is cut. That is why the fix is the budget *and* the detection, and why the regression tests sweep 1–5 days rather than asserting on the one trip length that was reported.

`evaluation/comparative_analysis.py` runs 68 queries in three tiers — hand-written, a generated city × category grid, and the chain tier added by issue #126 — through all three configurations and reports:

|---|---|---|---|---|---|
| **Fusion RAG** (Semantic+Graph+Keyword) | 0.231 | **0.517** | **0.967** | 1.000 | 0.91 |
| **Hybrid RAG** (Semantic+Keyword) | 0.121 | 0.250 | 0.659 | 1.000 | 1.05 |
| **Standard prompting** (no retrieval) | 0.000 | 0.000 | 0.438 | 0.000 | 0.78 |

**The table is weighted by query count, and that is a choice (#176).** Every mean above is over queries, so the 34-query grid tier carries more of it than the 24-query hand-written tier and far more than the 10-query chain. Which weighting the report quotes was unwritten until #176 asked. Weighting the three tiers equally instead gives Fusion **0.455** and Hybrid **0.204** against the 0.517 / 0.250 above — about 12% lower, with the ordering unchanged. Count weighting is kept because the alternative hands the chain tier, the one with the fewest observations and the weakest answer key, the same share of the headline as a tier three times its size. The per-tier and per-archetype breakdown, with n on every row, is `evaluation/comparative_analysis_breakdown.csv`:

| Tier | n | Fusion | Hybrid | Standard |
|---|---|---|---|---|
| grid (names its own category) | 34 | 0.642 | 0.317 | 0.000 |
| hand-written (natural phrasing) | 24 | 0.437 | 0.233 | 0.000 |
| chain (sequenced from an anchor) | 10 | 0.288 | 0.063 | 0.000 |

The ordering of the tiers by difficulty is the finding #50 reported and this makes visible: the grid is the easy half and it is the largest slice.

**Three queries were removed and four added, and both moves are the measurement correcting itself.** A cell needs enough gold POIs before `recall@8` can grade it: against a one-element answer key the metric takes exactly two values, so the query flips a coin and the table reads the result as a retrieval failure. Three queries were in that state, all Berlin/food, two of them scoring 0.00 — the elimination rule was a truthiness check, i.e. a threshold of zero (#175). The four additions are chain anchors (#176, below). `MIN_GOLD = 5` now applies to all three tiers, the rejects are published rather than dropped in silence (`UNDERCOVERED_QUERIES`), and per-cell key coverage is written to `evaluation/gold_coverage.csv`. On the committed per-query results the thresholds 4 through 7 are indistinguishable — they drop the same three queries — so the number comes from the metric's resolution rather than from the outcome it produces. The effect on the table is +0.019 normalized recall for Fusion and +0.012 for Hybrid, and it changes no ordering and no verdict.

**Read the second column, not the first.** Recall@k divides hits by the size of the answer key, but only `top_k` places are retrieved and the median key holds more than that, so the first column measures the key's size as much as the retrieval — a query with 85 answers and 8 slots is capped at 0.094 however good the retriever is (#49). "Recall vs attainable" divides by `min(top_k, key size)` instead, per query, so 1.0 means the retriever found everything the pool had room for. Both are tested pairwise; they agree here, and where they ever disagree the disagreement is the finding.

**The chain tier is where the graph earns its place, and it is no longer the least measured tier in the set.** Ten queries — one per city centre plus four mainline stations each, rotated across archetypes so the tier is not a property of one traveler — ask what can be *sequenced* from where the day starts, which is the relation `SERVES`/`REACHABLE` exist for and the one neither of the other tiers can express. Fusion reaches 0.288 of the attainable against Hybrid's 0.063, a fourfold gap (paired Wilcoxon, p = 0.016 at n = 10).

It held six queries until #176, and the six were both underpowered and slightly optimistic: Fusion read 0.333 there, and the four anchors added since are harder. The tier grew inside its own rule rather than against it — the 15% ceiling that keeps a traversal-defined key from carrying the headline (#48) is a proportion, and at this set size it permits ten. What the extra four bought is visible one paragraph down: archetype precision in this tier now separates the configurations at p = 0.0039, where at n = 6 the same test returned p = 0.063 and resolved nothing. Beside it sits a metric no answer key can inflate: of the pairs the two edges admit from an anchor, **77% are not actually doable in sequence** — the second place has already shut by the time you could reach it. That is what the hour constraint removes, and it is measured without reference to any gold set. **The second leg's ten minutes was then re-opened and kept** (issue #144). #126's own sweep had made fifteen look defensible — precision flat at 0.624 → 0.631, recall up 28% relative — and left the choice as "measured, not selected". What was missing is that the chain enters fusion as a fourth ranked list, so growing it moves the fused top-8 whatever weight it carries; threshold and weight were therefore swept together (`evaluation/chain_threshold_weight_sweep.py`). Three measurements agree. At ten minutes every weight from 0.02 to 0.15 keeps the chain inside KN-2's 2–4 band; at fifteen **no weight does** — even 0.02 puts it at 5 of the top 8, so the weight cannot buy the threshold back. Catalogue share goes 28.3% → 36.1% in Paris. And the chain tier gains recall while losing the thing it exists for: fusion 0.333 → 0.375 against hybrid 0.042 → 0.063, narrowing the margin from 8.0× to 6.0× — the tier's answer key *is* the traversal, so a looser walk grows the key along with the result. Ten stays. The same sweep also settles a bound that had been provisional since phase 4: the acceptance criterion said 25% of the catalogue while Paris measured 28.3%, and the test shipped at 30% with a comment admitting the gap. The failure mode it protects against — raw two-hop expansion — measures 41–54%, so the bound is now **35%**: clear of the shipped threshold, rejecting fifteen minutes, and landing where KN-2 independently lands.

**Its answer key is partly circular, and is labelled as such.** A chain query's key is the traversal's own output kept to POIs Wikivoyage recommends (decision K1). The gate is what stops recall measuring self-agreement — a retriever can walk every edge in the graph and still score zero by surfacing places nobody recommends — but it does not make the key independent of the retriever the way the other tiers' keys are. These six queries are therefore reported under their own dependence level, `traversal`, rather than folded into an existing one.

These figures replace the previous revision's and are **not comparable to them**: they are measured on a different catalogue (2 cities × 400/300 POIs, against 8 × 150) and with a different query set (55 queries, rebuilt because only 6 of the previous 51 targeted a city that still exists). **They are also not comparable to the revision immediately before this one, and that break is worth stating precisely rather than leaving for a reader to trip over.** The query set grew from 61 to 67 when the chain tier arrived, and the six new queries carry large answer keys (37 on average against 8 retrieved slots), so the headline mean falls from 0.2578 to 0.2359 without any retrieval getting worse. Measured on the *same* 61 queries as before, Fusion goes 0.2578 → 0.2514 — a 2.5% relative cost, which is the chain displacing a few category matches on queries that never asked to be sequenced, paid back as archetype precision 0.9693 → 0.9713. The `near_transport` gold definition is unchanged; what changed is which queries are in the set. Two changes to the measurement itself came out of that rebuild and are worth stating, because both were silent failures rather than disagreements about method:

- **`near_transport` had stopped selecting anything.** The gold set counts a POI as "near a hub" within `GOLD_MAX_KM`, set to 6.0 km — twice the graph retriever's traversal radius, deliberately looser so a correct answer is not defined as whatever that one traversal returns. On the previous catalogue, where a city carried two hand-picked transport rows and one of them sat 23 km outside, 6 km discriminated. With real interchanges and a denser catalogue, **100% of POIs in both cities fall within 6 km of a hub**, so the constraint was a no-op and those queries were being graded against the whole category. Both radii came down together — traversal 3.0 → 1.0 km, gold 6.0 → 2.0 km — preserving the 2× ratio. At 2.0 km the gold set is 75% of the unconstrained one.
- **The same geometry had made the graph relation itself uninformative.** At 3.0 km, 96% of Paris POIs and 92% of Berlin's counted as near a hub, so `multi_hop_transport_to_poi` returned nearly the whole city. 1.0 km kept 18% and 55%, and matched what the queries ask for: a hub "within walking distance", which 3 km is not. That radius is now the *fallback* only — for a city with no committed timetable — since #126 rebuilt the relation on solved journey times (§3.3); at 15 minutes it holds 70% of Paris and 74% of Berlin, and the two rules overlap by a Jaccard of only 0.17 / 0.34, so this is a different relation rather than a re-tuned one.

(Numbers above are from the 700-POI Wikidata/OSM catalogue [§3.1] with real `sentence-transformers`+FAISS semantic embeddings [§3.3, issue #4]. Full per-query results: `evaluation/comparative_analysis_results.csv`; aggregated: `evaluation/comparative_analysis_summary.csv`; pairwise tests: `evaluation/comparative_analysis_significance.csv`. Reproduce with `python evaluation/comparative_analysis.py`.)

**Reading these results honestly:**

- **Archetype-category precision is the one clear, statistically real gap** (Fusion 0.967 vs. Hybrid 0.659 vs. Standard 0.438): only Graph-RAG has direct `ArchetypeProfile -[PREFERS]-> POI` edges, so only the fusion configuration systematically surfaces POIs matching the *traveler's segment* rather than just the query text. Paired Wilcoxon across the same 68 queries puts it at p < 0.0001, with Fusion ahead on 53 queries, behind on 1 and tied on 14. It holds in **all three** tiers separately — p = 0.00033 hand-written (n = 24), p = 0.000011 generated (n = 34), p = 0.0039 chain (n = 10) — so it is a property of the architecture rather than of how the questions are phrased. The chain tier is new to that list: at the six queries it held before #176 the same test returned p = 0.063 and resolved nothing, which is why that issue raised the tier to ten. At 300–400 POIs/city there are ample genuinely off-archetype POIs for this structural advantage to matter; at the original 10-POI scale precision differences were muted simply because there was little room to be wrong.
- **Multi-hop recall is now graded against an independent answer key, and on that key Fusion does separate from Hybrid.** The gold set used to be *every* POI of the queried category within `GOLD_MAX_KM` of a hub. Both halves of that come from `GraphIndex.city_pois` and the hub-distance walk — the same traversals the graph retriever dispatches to — so a query naming its category next to a transport word made retrieval a subset of the answer key *by construction*, and its recall measured that the retriever agrees with itself. 22 of 55 queries sat in that bucket. The metric also had no headroom: the median gold set held 32 POIs, so at `top_k=8` a perfectly ordered retriever topped out at 0.317, and Fusion's 0.162 against Hybrid's 0.154 did not survive a paired test (p = 0.49).

  The key is now built by `pipeline/retrieval_gold.py` from **Wikivoyage** listings — `see`, `do`, `buy`, `eat` and `drink` — matched one-to-one onto catalogue POIs by QID, then by coordinate within 250 m, then by name. Wikivoyage is written by travellers listing what is worth going to and owes nothing to Wikidata sitelinks, OpenStreetMap tagging, or this project's graph, which are the three signals both the catalogue and the retriever are built from. Membership of it is therefore an independent statement that a place is worth recommending, and retrieval can return any number of category matches and still score zero. 409 of the 654 catalogue POIs carry a Wikivoyage listing; the median query's answer key falls from 32 POIs to 17, which also lifts the mean reachable ceiling at `top_k=8` from 0.317 to 0.512 — so Fusion's 0.253 is 49% of what is attainable, against 51% before, on a key that is now worth attaining. The key is committed as `evaluation/retrieval_gold.csv` so the evaluation and the test suite stay offline; only rebuilding it needs the network.

  Removing the circularity made Fusion's lead **larger**, not smaller — the outcome that a self-grading metric would have hidden. Against the independent key, Fusion's recall@k is **0.231** to Hybrid's **0.121** (mean advantage 0.110, 52 wins / 3 losses / 13 ties, p < 0.0001) where the same comparison on the old key gave 0.088. The earlier finding that Fusion's advantage lay in *archetype targeting* rather than recall was an artefact of two things at once: an answer key that rewarded returning any member of a category, and a ranking that could not tell the Louvre from an obscure institute (issue #63). With both fixed, Fusion leads on recall, archetype precision (0.967 vs 0.693) and itinerary coherence (0.80 vs 1.12 km/stop) simultaneously.

  `dependence_level` is kept in the per-query CSV, but it no longer reports circularity — it reports *difficulty*. A query naming its category tells the router where to look; one describing an intent ("somewhere calm by the water") does not, and 44 of 68 queries are of the harder kind, so the headline is not carried by the easy half (issues #48, #49).

**The proposal's metric is 0.0, and that is a weaker result than it looks.** Not one narrative in any configuration named a place belonging to the other city. The three arms therefore do not differ in the way this metric can see. What the number establishes is that the #56 prompt design holds up under a real generative model across 1,352 place mentions; it does not establish that Fusion RAG reduces hallucination relative to the others, and the table should not be read as saying so.

**The second column is where the model still departs from its instructions.** The system prompt says "never mention or suggest any other place, attraction or venue", and 2.4% / 1.3% / 1.4% of named places are ones the model was never shown. They are reported separately rather than added to the first column because **every one of them was real and in the right city** — the 23 mentions reduce to four names across 15 distinct prompts: "Île de la Cité" (7 of the 15), "Pariser Platz" (3), "Place de la Bastille" (3) and "Latin Quarter" (2). Calling those geographical hallucinations would be false. They are the #56 failure mode surviving in a milder form: the model supplies a correct geographic fact from its own parametric knowledge — Notre-Dame *is* on the Île de la Cité — that nothing in the pipeline put there or checked.

Three honest caveats:

- **Fusion still scores worst on the second column (2.2% vs 1.3% / 1.2%), but the Paris effect this used to rest on has mostly gone with the counts.** Per city, Fusion is now 7 of 233 mentions in Paris against 4 of 226 in Berlin; before #173 it was 17 of 241 against 6 of 241, and the Paris-heavy split was the whole of the explanation offered here. At six and four the split is two mentions wide and carries no weight — Fusion's ordering above the other two arms is now a difference of four and five mentions in total, which is not a finding. What survives is the qualitative point: the ungrounded names are centre-of-Paris geography ("Île de la Cité") attached to Notre-Dame, and Fusion is the arm that reaches Notre-Dame most often.
- **Standard prompting's n is smaller than it looks.** It retrieves nothing, so its candidate set does not depend on the question: 68 queries collapse onto 14 distinct prompts (2 cities × 7 archetypes), and only 2 of those 14 contained an ungrounded mention. Its 429 place names come from weighting those 14 narratives back out to 68 rows. The weighting reproduces exactly what a 201-call run would report, but the independent observations behind that arm are 14 narratives, not 67.
- **One half of the issue's definition is unmeasured.** A name the catalogue has never heard of cannot be found by gazetteer lookup, and this module deliberately does not attempt open-text entity extraction. The only signal on it is the zero-context probe (`llm_hallucination_probe.csv`): asked to name five places with no retrieval at all, the model produced 5 lines per city, of which the catalogue matches 4 (Berlin) and 3 (Paris). **Those 3 unmatched lines are an upper bound, not a count of inventions**, because the probe cannot tell a place the catalogue lacks from one it holds under another name — of the three, "Notre-Dame Cathedral" is in the catalogue as *Notre-Dame de Paris*, "Champs-Élysées" sits beside *jardins des Champs-Élysées* and *Théâtre des Champs-Élysées*, and only "Checkpoint Charlie" is genuinely absent. Resolving aliases needs the entity linking this module does not do; what the probe does establish is that the no-retrieval arm is the only place in this system where a place name reaches a user without having passed through retrieval and routing at all.

All 106 generations are cached in `evaluation/hallucination_generations.json` and committed, so the CSVs above can be re-derived without spending quota: a re-run reports `0 generation(s), 109 served from cache`. The file holds 214 entries rather than 106 — the pre-#173 generations are still in it, keyed by a prompt nothing builds any more. They are dead weight, not a second opinion; nothing reads them and no run can hit them.

#### What the prompt change fixed (issue #173)

The narrative below is from the first run, on a Berlin itinerary whose stops sit 280 m apart:

> *"At 1:02 PM, you'll reach the **Reichstag** […] A **64-minute walk** brings you to the iconic **Brandenburg Gate** by 2:06 PM."*

The 64 minutes was 2:06 minus 1:02 — an hour inside the Reichstag plus the four-minute walk. The facts block gave arrival clocks and nothing else, so a difference between two of them was the only duration the model had, and it spent the whole of it on the walk. `#132`'s own metrics could not see this: every place named was real, in the right city and in the prompt, so `wrong_city` and `unshown` both read zero on a narrative containing a 16× error. It is the blind spot of a metric that grades *places* and not the *relations* asserted between them.

On the same itinerary after the fix, the model writes: *"**Brandenburg Gate** – Only a four‑minute walk away"* — the prompt states `4 min walk, 0.3 km from the previous stop`.

Across the whole re-run, **359 travel-duration claims were made and 351 of them (97.8%) equal a leg stated in that narrative's own prompt to within a minute**; the eight residuals are, on inspection, the day's total walking time or a stated waiting time that the extraction counted as a leg, so no claim in the run traces to a number the prompt did not contain. The same extraction over the pre-#173 generations finds nine such claims in 106 narratives: three are the day's total and correct, and the remaining six are all the shape this issue is about — a difference between two arrival clocks, offered as a walk (64, 64, 73, 49, 48 and 15 minutes). Two of the six were checked against catalogue coordinates when #173 was filed and are wrong by 16× and 2.7×; the other four were not individually verified. **Measured claims went from 6 to 213 and their accuracy is what changed the picture**: the model states leg durations constantly now, and takes them from the prompt.

Two things this does **not** fix. Unmeasured proximity language is unchanged: 63 of 106 narratives still use a bare "stroll", "short walk", "steps away" or "nearby" with no number attached, against 60 of 108 before — 79 such phrases against 77. The fix did not replace vague language with numbers; it added correct numbers beside it, and the vague half stayed exactly where it was. Those phrases are not false statements and this measurement does not grade them, but they are the same rhetorical slot the wrong number came out of. And the general check — validating every distance and duration a narrative asserts against `street_network/*.npz` and the GTFS timetables — is not built; it needs no model call and the data is already committed, which is what makes it the natural next step.

#### Geographic constraint validation (issue #177)

`evaluation/geographic_validation.py` grades **the relations the narrative asserts between places**, as a third metric of this measurement and never a term added to the other two — those count place names, this counts claims. It exists because §3.5's own blind spot has a name: the 64-minute walk above was `wrong_city = 0`, `unshown = 0`, and 16× wrong. It costs nothing to run: it scores the committed generations and calls no model.

| Config | Claims | numeric / vague | Unresolved | Matches some stated leg | True of the street network (numeric) | True of the street network (vague) |
|---|---|---|---|---|---|---|
| Fusion RAG | 247 | 185 / 62 | 65 | 0.957 | 0.295 | 0.515 |
| Hybrid RAG | 245 | 169 / 76 | 68 | 0.988 | 0.321 | **0.350** |
| Standard prompting | 212 | 158 / 54 | 60 | 1.000 | 0.521 | 0.548 |

**The model does not invent numbers.** 96–100% of its numeric claims equal a leg the prompt actually stated, which agrees with the independent extraction #173 reported (97.8%). A stricter column — the claim against the *specific* leg it was attributed to — reads 0.62 / 0.61 / 0.80, but that is a lower bound on the model and partly a statement about this module: attributing a claim to the right leg needs the narrative to say which two stops it means, and where it does say so unambiguously (a bold heading) the same column reads 0.81 / 0.74 / 0.87. 27% of claims cannot be placed on a leg at all and are reported rather than guessed at.

**The numeric column is mostly measuring the harness, not the narrator.** 76–88% of duration claims *understate* the real walk, and the reason is upstream of the model: `hallucination.build_prompts` plans with `use_real_routing=False`, so every leg the narrator is told is a straight-line estimate. Against the committed street networks that estimate is a median **1.29×** short (p90 1.90), and only **48%** of stated legs fall within tolerance of the real footpath time. A perfectly faithful narrative is therefore still wrong about the city. **This is a property of the evaluation harness, not of the shipped product** — `views/itinerary.py` has planned with `use_real_routing=True` since #160. Closing it means re-running every generation in the measurement, which #177 ruled out; it is reported here instead, and it is the first thing to fix if this metric is ever quoted as a product number.

**The vague column is the clean one, and it is the first metric in §3.5 that separates the three arms.** It is graded purely against street distance — is a leg called "a short walk" or "a stroll" actually within `HYBRID_WALK_THRESHOLD_KM = 1.2`, the distance `travel_modes.py` already documents as the point a traveler stops walking by choice — so the straight-line estimate never enters it. Hybrid calls **65%** of the legs it describes that way longer than that threshold, against 48% for Fusion and 45% for Standard, and the ordering follows the days' geometry (km/stop 1.05 / 0.91 / 0.78). Every other number in §3.5 reads 0.0 / 0.0 / 0.0 or is grounded by construction in all three arms; this one distinguishes them, and it does so on exactly the property the arms differ in.

**Standard prompting scoring best here is not a quality result.** It retrieves nothing, so it plans the tightest days in the catalogue, and short legs are easier to describe truthfully. Read the column as a measure of how walkable a configuration's days are, not of how good its retrieval is.

- **Structural grounding rate is 1.0 for any retrieval-based config and 0.0 for standard prompting by construction** — every document either retrieval layer returns is a real node in the knowledge graph, so this is a structural hallucination-risk proxy, not a measurement of a generative model actually hallucinating (the default `TemplateLLMClient` cannot invent text). It was called `grounded_entity_rate` until #132, and the name was doing real damage: it read as the proposal's hallucination metric in every table it appeared in, while the Wilcoxon test on it could only ever answer "identical". The measurement it was standing in for is now its own thing — `evaluation/hallucination.py`, which generates narratives under all three configurations and grades every place name in them against the catalogue and against what the model was shown. That measurement needs a key and a live endpoint, so CI cannot verify it; its generations are cached to a committed JSON file so the committed CSV is reproducible without re-spending anyone's quota.
- **Itinerary coherence (km/stop) still separates Fusion from Hybrid, and #122 narrowed the gap on purpose** (Fusion 0.91 vs. Hybrid 1.05, paired p = 0.0028): *which* POIs a config selects has real consequences for how walkable the route is, and Fusion's archetype- and proximity-aware selection produces the tighter one. The gap used to be wider — mean advantage 0.2543 at p = 6e-05 — and #122 is what closed part of it: guaranteeing a city's three best-known places into every plan and making them expensive to drop adds distance by construction, because a landmark sits away from the centre cluster.

  **That change also costs this configuration a comparison it used to win, and the number is here rather than in a footnote.** Against standard prompting, Fusion's km/stop was previously indistinguishable (mean advantage 0.0015, p = 0.76) and is now **worse** (−0.1401, p = 0.00011): a no-retrieval config plans from a pool that was never dense around the centre, so it had less compactness to give up. The metric measures compactness, not quality — a Paris day that walks 0.91 km per stop and contains the Eiffel Tower is not a worse day than one that walks 0.77 km per stop without it — but the direction is real, it is caused by a deliberate change, and §5's #122 entry states what was bought with it.

## 5. Known limitations & honest gaps vs. the proposal

- **The chain is on by default now, and the gate it passed is a narrow one.** Issue #126 shipped the hour-aware traversal behind `ROAMWISE_GRAPH_CHAIN` precisely because it fires on every plan — the anchor is the city centre, not a keyword — and the flag opened only after the full 12/15/18-hour grid showed nothing regressing: stops/day 9.417 → 9.444, km/stop 0.637 → 0.628, preference match 0.5858 → 0.5859, categories/day 3.167 → 3.194, arrivals at a closed venue 0 in both arms, both meals filled on all 72 days. What that gate does *not* establish is that the chain makes plans better; it establishes that it makes them no worse while adding a relation the other retrievers cannot express. The flag still works in both directions (`ROAMWISE_GRAPH_CHAIN=0`), which is what keeps that comparison reproducible.
- **The chain's RRF weight was chosen twice, and the first choice was measured wrong.** Phase 4 swept it at `top_k=8` and picked 1.5. That is eight retrieved places, not the seventy-two a three-day trip retrieves, and the chain's share of the top 8 depends on how long the lists being fused are — at the real pool size 1.5 puts it at 5.9 of 8 and at 8 of 8 in one cell, which is the domination checkpoint KN-2 exists to catch. Re-swept at 72, `RETRIEVER_WEIGHTS["chain"]` is 0.15. The value is far below the other three because the chain contributes 144 ranked documents where the graph contributes two short lists, so per-document weight has to be small for total influence to be comparable — #63's finding restated. The error is recorded rather than quietly corrected because a swept number is only worth what its conditions were.
- **The chain can only ever see the POIs whose opening hours somebody observed.** 277 of the catalogue's 654 rows carry a category default — "a museum is usually open 10–18" — that nobody checked. A sequencing constraint is satisfied for free by every one of them, so the chain excludes them and is bounded by what is left: **PAR 237/371 (64%), BER 140/283 (49%)**. This is a data-coverage limit rather than a defect, and the filter is what makes the relation say anything at all — without it the chain reaches roughly half of each catalogue and separates nothing; with it, 28% (PAR) and 18% (BER). Stated here because unstated it would read as a defect.
- **The graph's transit edges are a daytime median, and the chain they support inherits that.** `SERVES` and `REACHABLE` (`knowledge_graph/build_graph.py`) carry journey times solved from GTFS by `pipeline/build_transit_matrix.py`, which takes the median over thirteen departures between 08:00 and 20:00. Night service is outside the sample. Measured over the committed matrices, 96% of the chains this relation supports depart before 20:00, so the exposure is the remaining 4% — those are priced at a daytime rate, which for a late second venue is optimistic. Widening the sample is a pipeline change, not a retrieval one, and it is not made here.
- **Where a city has no committed timetable, the same edges fall back to a walking estimate — and say so.** Both relations carry a `source` of `"transit"` or `"haversine"`, and the fallback is the 1 km / 10-minute walking circle rather than a solved journey. This is written down rather than hidden because the two are different claims: minutes off a timetable and minutes from dividing a straight line by 4.5 km/h are not interchangeable, and a graph that presented them identically would let the weaker one be reported as the stronger. Both cities the project ships hold a real matrix (100% of POIs, hubs and centres match it), so nothing currently in the repo runs on the fallback.
- **The destination list is two cities, and that is a real limitation as well as a deliberate trade.** Depth per city roughly doubled reference-list coverage (§3.1), and Fusion RAG and the agentic orchestration are unaffected — retrieval is filtered by `destination_id` and works *within* a city, and the orchestrator's flow is unchanged with only the destination node's option set narrowed. What it costs is the destination-*selection* half of the pipeline; see the next two points.
- **Crowding no longer discriminates between destinations — and the previous eight-city version only appeared to.** Simulating all 729 preference profiles × 12 months, Paris and Berlin return an identical crowding profile (`L,L,M,H,H,H,H,H,H,H,M,M`), so `crowd_penalty` cancels in every month-to-month comparison and the travel month changes the chosen destination in **0 of 729** profiles (it changed all 729 before). The root cause is a design mismatch, not the city count: `forecast_city` computes `crowding_z` against *each city's own* history, which by construction erases level differences between cities — the right tool for "which month is busy here", the wrong one for "which city is busier". Two European city-break destinations with correctly-measured seasonality genuinely do look alike (amplitude 1.43× and 1.77×). The eight-city version discriminated because its country-level proxy was wrong: Vienna showed January–March "high" and April–May "low", which is *Austria's ski season* pasted onto a city, and that error made VIE win 25% of all destination choices. So the honest reading is that this capability was never working — the previous data hid a broken comparison behind a plausible-looking one. Resolving it needs a between-city measure such as bed-occupancy rate rather than a within-city z-score, and it is tracked as an open decision rather than claimed as done.
- **Demand data is regional, and its coverage lags unevenly.** The series is now Eurostat's `tour_occ_nin2m` at NUTS 2 granularity rather than the country-level `tour_occ_nim` proxy, which matters because the forecaster consumes seasonal *shape*: France peaks in August at 2.35× its annual mean while Île-de-France sits at 1.06×, so the national series changed the crowding label in 8 of 12 Paris months. Berlin is its own NUTS 2 region (DE30); Paris maps to Île-de-France (FR10), wider than the city but far tighter than France — and most cities are like Paris rather than Berlin, so this mapping needs checking per city rather than assuming. Two gaps remain and neither is fixable by changing source: the measure is **nights spent, not arrivals** (a three-night stay counts three; day-trippers are invisible; Eurostat publishes no monthly regional arrivals series), and German regional returns lag ~20 months behind French ones. The lag is handled rather than hidden — `models/forecasting.py` computes its horizon from today rather than from the end of the series, and `ForecasterAgent` reports `data_through`, `horizon_months_used` and `requested_month_available` with every forecast. Before that fix, Berlin silently returned January 2025 for a July 2026 query and was labelled `low` when its real July is `high`, which made it win every summer comparison purely because its data was published late.

  That fix reached the agent and not the screen beside it. The Demand forecast tab called `forecast_city(city, horizon_months=12)` directly, so it kept counting from the end of the series and rendered the result under the title "Forecasted monthly visitors (next 12 months)": measured on 2026-08-30, Berlin's twelve bars were 2025-01 … 2025-12 — **twelve months of which twelve had already happened** — while Paris's were 2026-01 … 2026-12, of which eight had. Two cities, two different "next 12 months", both labelled the same. Issue #161 moved the conversion into `forecast_window()` and pointed both the chart and the agent at it; both cities now open on the current month, the title is generated from the window rather than asserted over it, and the tab states how far past its last real observation each city is being extrapolated (20–31 months for Berlin, 8–19 for Paris, on the same date). The number that fix does not change is the one underneath: Berlin's forecast is now a correctly-dated extrapolation from a series that still stops in 2024-12, and refreshing that series is data work (`pipeline/build_demand.py`), not code.
- **Whether a venue still operates is only partly knowable from the sources.** The catalogue drops food, nightlife and shopping rows that Wikidata marks with a closure date (`P576`/`P3999`), and demotes any that OpenStreetMap does not corroborate below those it does. Neither signal is applied to the sight categories, and deliberately so: `P576` records that an *entity* ended, not that its site is gone, and the Berlin Wall (1989), the Bastille (1789) and the Kaiser-Wilhelm-Gedächtniskirche (1943) are among the best-known things to go and see in their cities. The two signals are complementary rather than redundant — Café de la Régence carries a closure date, while Café Josty, Café Bauer and Moka Efti, all long gone, carry none and are typed simply "café"; only the missing OSM counterpart separates them from Konnopke's Imbiss. Across every venue checked by hand the split was clean (10 of 10 defunct unmatched, 6 of 7 operating matched), but it is evidence rather than proof: Maxim's is open and unmatched, and survives only because Paris has enough food slots for a demoted row to still make the cut. A venue that closed last month, with no Wikidata edit and a stale OSM node, would pass both checks.
- **The catalogue carries no price tier, so the Budget preference cannot reach the choice it most obviously should.** `price_level` is derived from OpenStreetMap's `fee` tag (`build_catalogue.py`), which answers *whether* a place charges admission and never *how much*: it only ever holds 0 or 1, and 574 of 654 rows take a category default because OSM carries no `fee` tag for them at all. Two consequences, of different severity. The first was a bug and is fixed: `plan_trip` offered a `max_price_level` filter documented "1=budget, 3=splurge" whose default threshold was 3, so the condition `price_level <= 3` was true for every row in the catalogue and the filter had never removed a single POI in the project's history — a capability the signature advertised and the data could not support (issue #67). The second was a real limitation and is now partly closed: all 61 `food` POIs used to carry `price_level = 1`, so nothing in the data separated `L'Ambroisie` (three Michelin stars) from `Polidor` (a modest bistro), and a Budget Backpacker was routed to either with equal willingness. Issue #71 put a real tier on 29 of those 61 (spread 32/10/14/5 across the four levels) and on 28 of the 41 `nightlife` rows; `shopping` gained nothing, because the source carries no tier for shops. So the budget slider now has something to act on where budget most obviously bites, and the remaining 32 undifferentiated `food` rows are the residue rather than the whole set. Mining the descriptions does not rescue it — only 4 of the 61 mention Michelin, and `Le Jules Verne`, `Maxim's` and `Taillevent` are not among them. The deeper cause is that the catalogue is selected by *fame*, so the cheap neighbourhood restaurant a backpacker actually wants was never a candidate; closing this needs a price-bearing source rather than a better rule over what is already here — and issue #71 has now measured which source and what it buys, in the entry below. What the preference does still reach is the archetype: holding every other slider fixed, Budget=Low segments to Budget Backpacker and yields a Paris plan that is 35% free-to-enter, while Budget=High segments to Luxury Traveler and yields 0%. That share is now reported to the traveller instead of being consumed by a filter that matched everything.

- **180 rows' opening hours and 60 rows' price tier come from Google Maps, and that is a redistribution question this report should not bury.** Two of the gaps above — 60.2% of opening windows being a category default, and every `food` row carrying the same `price_level` — were data-coverage problems rather than modelling ones. Issue #71 measured what a richer source buys, and then applied it: `pipeline/enrich_gmaps.py` writes the scraped values into `poi.csv`, and `hours_source`/`price_source` name `gmaps` row by row so no consumer has to guess which values these are.

  **It fills gaps rather than overwriting, and that rule was chosen on a measurement rather than on principle.** The enrichment covers 326 rows, but 194 of those already carried an OSM tag. Overwriting them buys **no coverage at all** — the contribution is entirely the 132 rows where OSM was silent, so coverage is 59.9% either way — while costing three things. 58 of the 194 OSM tags carry rules a seven-day scrape cannot express: the Eiffel Tower's is `09:30-23:45; Jun 21-Sep 02: 09:00-00:45; Jul 14,Jul 15 off`, which is summer hours and a Bastille Day closure, and Sainte Chapelle's is three separate seasons. On 19 of the 194 the two sources disagree about which *days* the venue opens at all, and only 36% agree exactly — so overwriting silently picks a winner on every disagreement. And every overwritten row would enlarge the amount of third-party content in a public repository for nothing. An earlier revision of this work did overwrite, and the numbers here are from the version that does not.

  **The one exception is measured too.** A tag claiming the same schedule seven days a week — `Mo-Su 10:00-18:00`, or a bare `09:00-18:00` — is not really an answer about days, and that is the shape an OSM tag takes when nobody filled in the detail. Where such a tag carries no season or holiday rule and actually disagrees with the scrape, the scrape wins: 44 rows are day-blind with an enrichment behind them, 24 of those disagree, and the other 20 are left untouched so no row changes for nothing. That is how the Ménagerie du Jardin des Plantes stopped being scheduled for 09:00 against a 10:00 opening, and how a bar tagged `Mo-Su 07:00-00:00` acquired the Sunday closure it actually keeps.

  **And where the two disagree about days rather than minutes, the scrape decides.** A half-hour difference is noise between two records of one schedule; a day one source calls open and the other calls shut is a different claim about the place, and it is the one that puts a traveller in front of a locked door. 24 rows were resolved that way, and the OSM tag's calendar-scoped clauses are carried across rather than dropped — `PH closed`, `Jan 01 12:00-18:00`, a whole seasonal range — because the grammar lets a later rule override an earlier one for the dates it covers. That is not cosmetic: the scrape claims parc Montsouris shuts on Tuesdays, which no public park does, and the seasonal rules kept from its OSM tag override that claim on every date they cover, so the park resolves to 07:00–20:30 on a September Tuesday and 07:00–17:45 in December.

  **Coverage.** Opening-hours coverage goes from **39.8% to 59.9%** — 197 rows from OSM, 180 from the enrichment, 277 still a category default. `price_level` stops being one value: the four tiers hold 371/31/21/5 rows against a flat 428 before, and no OSM `fee` signal was replaced.

  **What it changes in the itinerary, measured.** Two arms over 2 cities × 4 archetypes × 3 days, with the graph, retrieval and candidate pool built once and shared, so the only variable is the data. Plan *volume* and *coherence* move slightly in the right direction — 7.71 stops/day and 0.514 km/stop become 7.79 and 0.482 — but that understates the effect, because the stops themselves change: **60.3% of selected stops are common to both arms, so 92 of 232 changed**. The plan stays the same size and is made of different places. Audited against the enrichment's verified hours, stops scheduled at a closed venue fall from 5 of 101 (5.0%) to **0 of 102**. That figure is close to tautological for the rows the enrichment supplied, since those are the hours the audit checks against; what it does say is that none of the 197 rows still carrying an OSM tag put a planned stop at a closed door across these eight itineraries.

  **What this costs, stated rather than hidden.** The source's terms do not permit redistributing its content, and this repository is public with its catalogue as a committed file. Those 240 field values are therefore in the repository against those terms — a deliberate choice, made with the alternative measured and available: the same gap is addressable from redistributable sources (Overture Maps Places under CDLA-Permissive for hours, Foursquare Open Source Places under Apache-2.0 for price tier), and that route was considered and not taken inside this project's remaining scope. A reader evaluating this catalogue as a data artefact should weigh the 59.9% coverage against that, which is why `hours_source` and `price_source` name the origin per row instead of flattening everything to "observed". The scrape itself, its cache and its per-place records are not in the repository; what is committed is the applied values and the script that applies them.

  **What is still missing.** 277 rows (42.4%) still take a category default for opening hours, and those defaults are measurably wrong in places — against the scraped hours, `nature` defaults to 0–24 where the real median is 8:00–21:30, and no category default carries a weekly closing day although museums average 0.86 and `culture` 1.33. The catalogue no longer holds a row where the two sources disagree about opening days. The intraday busyness profiles are in the catalogue as `data/crowding.csv`, and what they reach is the next entry.

- **The best-known place in a city used to be the cheapest thing to drop, and what fixes it costs distance.** Issue #122's finding: a Paris plan never contained the Eiffel Tower, and a Berlin one never contained the Wall. `optimization/toptw.py` prices a skipped stop at one scalar `drop_penalty_m` (8,000 m of walking), so the solver values every candidate the same and the stop furthest from the centre cluster is always the cheapest to give up — however well known it is. Re-measured after #126 over 2 cities × 7 archetypes × 3 days (`evaluation/iconic_coverage.py`), **22 of 168 (city × archetype × best-known-POI) slots were filled**, and the loss was entirely the solver's: every iconic POI that reached the retrieved pool also survived `select_by_score`, in all 24 rows. It is not a retrieval problem and cannot be fixed as one — #122 measured that widening the pool from 72 candidates to the whole 371-POI Paris catalogue leaves the tower dropped and makes iconic coverage *worse*, because more candidates means more competition under a score that does not favour fame.

  Two things were wrong, and each is half the fix. **The solver had no way to be told a stop was worth more**, which is now a prominence-scaled drop penalty: a POI whose within-pool `scoring.quality` clears a threshold costs a multiple of the flat price to skip, everything else keeps it. That is deliberately not the idea `evaluation/toptw_scoring_ablation.py` rejected at #72 — that one reweighted *every* node with the selection score and cost stops and distance for a 4% move in its own objective; this touches the four to eight POIs at the top of a working set. **And the landmark was often not a candidate at all**: retrieval is archetype-driven, so the tower reached the pool for 3 of 7 archetypes and a Nightlife Seeker's Paris trip never had the option. `RouterAgent._with_iconic` completes the working set with the city's three best-known places from the graph, the same route `_food_pois` has taken since #20 and for the same reason — widening the *query* instead would change what the Fusion/Hybrid/standard comparison is measuring, so the retrieval layer is left alone and the pool is completed after selection. This was #122's item 4, recorded there as a product decision to be taken explicitly rather than absorbed: a Nightlife Seeker's Paris plan should be able to contain the Eiffel Tower.

  Both knobs of the penalty were swept together with the guarantee in place (`evaluation/iconic_penalty_sweep.py`, 13 configurations × the same 14 cells):

  | threshold | multiplier | iconic in plan | stops/day | km/stop |
  |---|---|---|---|---|
  | — | 1.0 (before) | 33/168 | 8.071 | 0.624 |
  | 0.99 | 1.5 | 65/168 | 7.976 | 0.763 |
  | **0.97** | **1.5 (shipped)** | **80/168** | **8.095** | **0.755** |
  | 0.97 | 2.0 | 84/168 | 8.048 | 0.815 |
  | 0.95 | 3.0 | 84/168 | 7.929 | 0.983 |

  The guarantee alone is the first row — 22/168 to 33/168 — which is the useful half of that number: making a landmark a candidate barely helps while the solver still prices it like everything else. Together they take it to **80 of 168**, and of the iconic POIs the router could have taken it now keeps **91.9%** against 37.9%. Of the 42 guaranteed slots (2 cities × 7 archetypes × 3 landmarks) **41 are filled**: every plan in both cities contains that city's three best-known places, with one exception recorded below.

  **The pair was chosen twice, and the first choice is recorded rather than quietly replaced.** Swept before the guarantee existed, the answer was 0.99 × 1.5 and 0.97 looked like it bought its extra coverage at half again the distance. Widening which POIs are candidates changed which threshold is efficient — 0.99 admits about four POIs of a working set and 0.97 about eight, so with landmarks guaranteed it is the second rank that 0.99 leaves behind — and on the re-sweep 0.97 × 1.5 dominates outright: more kept (80 against 65) at *less* distance per stop (+21.0% against +22.3%) and no cost in stops (+0.3%). A swept number is worth only the conditions it was swept under; this is the same lesson #126's chain weight recorded, met a second time.

  **What it spends is real and is not a rounding error.** Distance per stop goes 0.624 → 0.755 km, **+21.0%**, against the −55.3% #72 bought with the whole solver rewrite. Stops per day do not pay at all (8.071 → 8.095) and categories per day improve (3.071 → 3.262), so the whole cost is distance — which is what a landmark *is*: it sits away from the centre cluster, and keeping it means walking to it. No setting makes that free, and the pricier pairs make it worse for the last four slots (0.97 × 2.0 reaches 84/168 at +30.6%).

  Two limits remain, both stated rather than closed. **One guaranteed slot of 42 is still unfilled**: the Paris Nightlife Seeker's day starts at 15:00 and the tower is 5 km out, so the solver still drops it; 0.97 × 2.0 does fill that cell, and buying it costs every other cell another ten points of distance. And the penalty is priced in metres, so a landmark more than about 10 km off the cluster is dropped even at 1.5× — the window is deliberate and is what `test_a_landmark_far_from_the_cluster_survives_the_solver` sits inside.

- **The `beach` category is empty.** Neither city has one, so 2 of the 7 archetypes lose their strongest signal: "Beach & Relax" loses its top-weighted category (`beach: 1.0`) and "Nature & Adventure" its second (`0.6`). Both still resolve — the evaluation's Beach & Relax queries are graded against `nature`, which both cities answer from river and lake shores — but the archetype is exercised more weakly than the other five. A coastal third city would close this.
- **Personalization rests on a synthetic survey — and the half of it the report has been presenting as the mechanism turns out to be nearly inert.** `data/user_survey.csv` is 420 invented rows (§3.1), and two things are calibrated on it: the preference→category matrix `PREFERENCE_CATEGORY_WEIGHTS`, fitted by NNLS (#72), and the KMeans segmenter that names a traveler's archetype. Until #124 the report said "synthetic" and stopped there. `evaluation/survey_sensitivity.py` measures it: four perturbations of the survey × 3 seeds, each refitting both consumers and re-planning the same 14 trips (2 cities × 7 archetype slider settings, 3 days), every plan graded on the *shipped* matrix so no variant grades itself.

  | perturbation | matrix Δ (mean) | matrix top-1 ranking kept | archetype agreement | stop overlap | preference match |
  |---|---|---|---|---|---|
  | shipped | 0 | 100% | 100% | 100% | 0.510 |
  | reseed | 0.005 | 100% | 100% | **100%** | 0.510 |

  **Resampling the survey changes nothing at all.** Not approximately: a fresh draw from the same archetype centres produces the same archetype for every traveler and the same set of stops in every one of the 14 plans, three seeds running. The spread has to reach 0.32 — four times the shipped 0.08 — before the archetype clouds overlap enough for KMeans to mislabel anyone. The last row is a control rather than a scenario: labels permuted across rows, which destroys the survey↔`CATEGORY_AFFINITY` correspondence and moves every column. Without it "insensitive" would be indistinguishable from "measured nothing".

  **Which half carries it is the finding.** The control run decomposed — perturbing one consumer at a time — separates them cleanly:

  | control, decomposed | matrix Δ | matrix top-1 kept | archetype agreement | stop overlap | preference match |
  |---|---|---|---|---|---|
  | matrix only | 0.204 | 11% | 100% | **99.4%** | 0.5097 |
  | segmenter only | 0 | 100% | 14% | 44% | 0.460 |

  Scrambling the preference matrix past recognition — five of its six dimensions rank a different category first — leaves **99.4% of planned stops exactly where they were** and moves the preference match by 0.0004. Every bit of the dependence runs through the segmenter, i.e. through the archetype *label*, which selects the retrieval query (`archetype_query`) and the hour the day starts at (`DAY_START_HOURS`). The plausible mechanism: the label decides which candidates exist at all, and within that pool prominence, opening hours and the solver's geometry decide the rest, while the preference factor is one multiplier among several with a 0.15 floor under it. That is consistent with what #79 already found for one row of the matrix — moving the `adventure` slider from 0.1 to 0.9 changes none of the 24 selected POIs — and generalises it: the property is not special to `adventure`.

  **What this means for the report's claims.** Two corrections follow. The synthetic survey is not a scientific risk to the *itineraries*, which is the honest answer to the worry #124 was opened on: no plan in this measurement depends on which random survey was drawn. But §3.2's presentation of the NNLS matrix as the personalization mechanism overstates it — at the plan level that matrix is close to decorative, and the thing doing the personalizing is a seven-way label produced by KMeans over 42 hand-written numbers (`generate_data.ARCHETYPES`). Those 42 numbers, not the 420 rows, are the actual input; the rows carry no information into the matrix beyond seven means. Replacing the survey with real data (the Wikivoyage derivation #124 sketches) would therefore buy far less than it appears to unless it also replaces `CATEGORY_AFFINITY` and the archetype definitions themselves — which is a decision this measurement was run to inform, and is not taken here.

- **No live LLM by default; the Anthropic path specifically remains unexercised.** The default template-based "reasoning engine" performs real selection/synthesis over structured data but does not perform open-ended generation, so it cannot exhibit true hallucination — by design, to keep the system free and offline. §3.4.2 now demonstrates the *local* open-weight path (`LocalHuggingFaceLLMClient`, issue #54) end to end with a real generative run and a grounding check. The Anthropic-backed path (issue #7) is still implemented but not exercised in this report — it needs a paid, provisioned API key that no build environment so far has had, which is exactly the gap the local path was added to route around for free.
- **No live Neo4j, and no dead code pretending otherwise.** Named as an example ("e.g., Neo4j **or** NetworkX") in the proposal; this build uses NetworkX for zero external service dependency and full unit-testability, not because Neo4j is infeasible. Until issue #145 `GraphIndex` also carried a `backend="neo4j"` branch in every method, which advertised a capability that could not run: nothing ever wrote to a Neo4j database, the branches returned internal `element_id`s where the rest of the code expects `PAR001`, and no test touched them — while `neo4j` sat unpinned in `requirements.txt` as the only unpinned dependency, installed by everyone. Those branches are gone; what is left is the backend that runs. (LangGraph, the other named example, has a working alternative implementation — see §3.4.1 — so this gap is specific to the graph *database*, not the agent framework.)
- **The router is a time-window solver now, but its personalization is only partly grounded.** This entry previously read "routing is a 2-opt heuristic, not a full time-window vehicle-routing solver", and said that closing that gap meant a real time-window formulation which stayed out of scope. Issue #72 closed it: selection, day assignment, ordering and opening hours are one TOPTW model (`optimization/toptw.py`), and the six repair passes that used to sit on top of a geography-only ordering are gone. What is left is smaller but real, and all of it is measured rather than suspected. **The crowding factor is real now, but only half of what the issue asked for.** It returned a constant 1.0 for the project's whole history, and the reason is worth keeping: `ForecasterAgent` answers per city and per month, and a single city-month scalar multiplied onto every candidate rescales the pool identically, so it cannot change which stops an optimiser picks. `data/crowding.csv` (269 POIs, 35,141 hourly readings) gives it variation that does survive normalisation — the emptiest POI averages 12% busy and the fullest 80% — and a POI with no reading falls back to its category's mean rather than to no discount, so being unmeasured is not an advantage. Measured over 2 cities × 4 archetypes × 3 days, turning it on moves stops/day from 7.79 to 7.92, leaves km/stop flat at 0.49, changes 73 of 226 selected stops, and drops the busyness the plan actually walks into from **60.1% to 56.9%** (median 61 → 56).

  **The hour is shipped now too, and it was the larger half.** A POI's own day swings a median 72 points from trough to peak while POIs differ from each other by a standard deviation of 13, so the hour carries roughly five times the signal — and the router was on the wrong side of it: measured before the change, stops sat at **58.6% busy at the hour they were actually visited, against the 47.5% their own typical level predicts**, an 11.1-point gap — measured over the 273 stops in those trips that the series covers, since it reaches 41% of the catalogue. That is worse than chance rather than merely unmanaged, because the hours a day naturally fills are the hours everyone else fills too. The obstacle was real and is worth stating: a score is a static node weight, so the hour cannot be an input to it, and a time-dependent node reward is not something the TOPTW formulation has room for. What it does have room for is a *second node*. Issue #33 gives each measured POI one more copy per day, pinned to its own quietest three hours and priced below the day-wide copy, so choosing the hour becomes choosing a node — which a static weight can price. Issue #109 then did the same for the meal sittings, which #33 had left out on the grounds that a compulsory sitting carries no choice of hour — half true, and the half that was wrong held the entire residual: a sitting is pinned to a four-hour band, not to a minute, and inside the dinner band a restaurant runs 36% busy at its quietest hour and 100% at its busiest. Measured over 2 cities × 4 archetypes × 3 day lengths (`evaluation/crowding_hour_measurement.py`), the two together close the gap from **+11.1 points to −3.1** — stops now land *quieter* than the places' own averages rather than busier — and take exposure from 58.6% to 44.3%, for 1.3% of the stops (6.71 → 6.62 per day) and nothing measurable in distance per stop (1.025 → 1.028 km). Split by kind, sightseeing goes +10.7 → −2.1 and meals +12.1 → −5.1. It holds in all 8 city × archetype pairs and grows with the day: an 18-hour day reaches −4.7 where a 12-hour day, with less room to move a stop, reaches −2.3. Four things are honest to say against it. The two prices are knobs, and the sightseeing one past 8,000 m stops buying quiet hours and starts buying quiet by *not going* — at 16,000 the solver drops 30% of the stops, which is not a scheduling improvement. Meals need their own, lower price (1,500 against 4,000) for the opposite reason: a sitting cannot be declined, so at the sightseeing price the solver answers by rebuilding the day around a quiet restaurant and the sightseeing stops pay for it — the meal gap overshot to −9.4 while sightseeing went the wrong way, −0.4 → +2.1, and the trip lost 2.5% of its stops. A quarter of the gain is the extra node alone, before anything is charged for taking it. And the meal contract is the thing to check first here, because a sitting cannot be declined and a change that improved this gap by dropping one would look like a win in every other column: it is unmoved at every price in the sweep — 2.0 meals a day, both sittings filled on 100% of the 72 measured days. Where it still cannot help is a traveller whose own hours are the busy ones: a Paris Nightlife Seeker is the worst pair at +15.4, halved from +31.4 but nowhere near the rest, because a bar's quiet hours are the ones before it is worth going to. **What the factor cannot see is 44% of the stops it schedules.** `data/crowding.csv` covers 269 of the 654 catalogue rows (41.1%), which comes out at 56.5% of the stops an itinerary actually contains — the router already favours central, well-known POIs and the scrape reached those. The rest are priced at their category's mean and get no quiet window at all, so they are timed blind. Two things were measured before accepting that. The unmeasured half is **not a biased sample**: measured and unmeasured POIs are indistinguishable on popularity score (median 3.7 vs 3.7), sitelink count (17 vs 16) and monthly pageviews (715 vs 721), so this is a random 41% rather than the famous 41% — had it been the latter, every number above would be measuring the busy tail and calling it the catalogue. And the category-mean fallback is weak but not blind: holding out each measured POI and predicting it from its category's other members is off by a median 6.5 points (mean 8.5) against a between-POI spread of 13.2, so it recovers roughly half the signal. Closing the gap needs a source that is not this one, and the honest candidate — a monthly Wikipedia pageviews series, half-written already in `build_catalogue.fetch_pageviews` — would extend coverage of *which* POI is busy without touching *when*, because a monthly series cannot answer an hourly question. That is tracked as its own work rather than claimed here. **The traveller is now asked for five preferences, not six, and the sixth's removal is the honest answer** (issue #79). `adventure` fits to a row of all-zero weights, because the catalogue has no adventure-ish category of its own — `beach` was the nearest one the affinity table offered and it holds zero POIs in two inland cities — so its signal is absorbed entirely by `nature`, which it correlates with across the survey. Measured, with every other slider held at 0.5 and `adventure` moved from 0.1 to 0.9: **none of the 24 selected POIs change**, where `culture` changes all 24. It was not merely inert, either, which is what settled the decision: it still moved the KMeans archetype, so a traveller asking for maximum adventure came back classified a *Budget Backpacker* and got a different itinerary for a reason with nothing to do with adventure. Dropping the slider costs almost nothing measurable — the survey mean feeds the sixth feature, `user_survey.csv` and the k=7 model are untouched, and all seven archetypes stay reachable from the five remaining sliders (Nature & Adventure falls from 5.8% of slider profiles to 2.5%, reached through `nature`). The same issue removed `beach` from the fitted matrix and from the two archetype queries that asked for beaches in cities that have none; that change is deliberately claimed as *no behaviour change at all* — `preference_match` reads one category at a time and `_MAX_MATCH` is set by the `food` column, so the same POIs are selected before and after. What it buys is that the matrix and the queries stop describing a catalogue we do not have. **And the budget slider still does not read price.** This entry previously said issue #71's enrichment made it act where budget bites; that overstated it. `price_level` is read in exactly two places, neither of them the score: the free-entry share the orchestrator reports, and the per-stop *free* label in the UI. The slider reaches the score only through `shopping` (0.306) and `landmark` (0.095) — 0.400 of matrix weight against `culture`'s 3.205 — which makes it the weakest live slider by a wide margin: moving it end to end changes 2 of 24 selected POIs. It is labelled "Everyday or upmarket" rather than "Budget" for that reason, and its help text says cost is shown per stop rather than used to choose stops. **The shortlist is not a speed workaround, though it was described as one.** This entry previously read that a full 371-POI catalogue "did not solve in ten minutes", making `MAX_WORKING_SET = 120` sound like a concession to the solver. Issue #80 tried to reproduce that and could not: today a 371-POI solve takes **15.9s**, or 45.2s with the expensive swap operator forced on — `f34de0e` had since made that operator conditional on pool size, and the original measurement's conditions could not be reconstructed. The honest statement is narrower and about today's code: the ceiling is not where it was claimed to be, and raising `MAX_WORKING_SET` is affordable (220 POIs solve in 7.6s). What the shortlist actually is, is `select_by_score` — the only place the traveller's six sliders reach the itinerary, since the solver never sees the preference vector. So removing it would remove personalization however fast the solver became, and there is no measured reason to want it removed: stops do not improve as the pool grows from 40 to 371 (20 → 15 → 22). **And it costs no measurable stops either** (issue #77). The router used to report stops and km/stop against nothing at all, while recall on the same screen was reported against what was collectable — one number capped and labelled, the other uncapped, both asking to be read the same way. `evaluation/toptw_ceiling.py` supplies the denominator: the same model on the same candidates with travel between them free. Over 48 configurations (2 cities × 4 archetypes × 3 day lengths × 2 pool sizes) a shipped trip fills **1,178 of 1,308 stops, 90.1%** — median 90.9%, 2.71 stops missed per trip, and nine configurations exactly at the ceiling, all nine at the smaller pool. So reading the stop count against nothing overstated the shortfall by about a tenth, not by the factor the retrieval side had: recall sits at 49% of what is attainable against the router's 90%. A third arm settles what the gap is made of. The trip is solved from the shortlist, the ceiling was solved from the pool, so the shortlist's own cost was folded into the number; solving the *same shortlist* with travel free separates them. It separates them into nothing: the two ceilings are identical in 35 of the 48 configurations and differ by at most two stops in the other 13 — in **both** directions, the shortlist ceiling coming out higher in seven of them. That direction is impossible for an exact bound, since a subset cannot beat its superset, so it is the relaxed arm showing its own limit: both arms are heuristic solves under one fixed iteration budget, and the larger pool is the harder search. The shortlist's cost sits below that resolution (−4 stops across 48 configurations), which makes the conclusion stronger than a split would have been — effectively all of the gap is the geometry, and personalization is not being paid for in trip length. The ratio is shown in the System Logs screen beside the retrieval ceiling, read from the committed measurement rather than recomputed per plan: the relaxed solve has no distance pruning its search, so it costs more than the trip it annotates (9.65s for a Paris trip, 16.5s for its ceiling). `RouterAgent.run(with_ceiling=True)` computes it per-trip for anyone willing to pay that. **The candidate pool size was a knob nobody had chosen deliberately, and now it is one**: `RETRIEVED_POIS_PER_DAY` was 8, sitting at one extreme of a measured frontier that trades relevance against density in opposite directions (raising it to 60/day takes distance per stop from 1.582 to 0.659 km while taking mean preference match from 0.752 to 0.485). It is 24 since `f34de0e`, and the reason is that selection stopped being retrieval's job: the score and TOPTW choose from the pool, so a wider pool is something to choose *from* rather than noise to wade through — against the pre-#72 router the gain roughly doubles, +15.8% stops and −55.3% km/stop at 24 against +7.8% and −42.7% at 8. The same knob is still what decides whether the diversity cap binds at all. **Even so, a whole category of the catalogue could not be reached by anyone.** Asking what a *plan* contains had never been paired with asking what the catalogue can even offer, and the second question had a much worse answer: taking the union of every (city × archetype) retrieval pool — the set of POIs some traveller could be shown — 63.8% of the catalogue was reachable on a three-day trip while `religion` sat at **1 POI of 84**. Four of the two cities' twenty-four best-known places were among the 83 nobody could see: Notre-Dame de Paris, the Panthéon, Sacré-Cœur and Berlin Cathedral. Two independent faults, both of which had to be fixed (issue #113, measured by `evaluation/retrieval_coverage.py`). The graph retriever ranked an archetype's preferred POIs on one affinity × prominence list and cut it at `top_k`, which starves the weakest category whenever the stronger ones can fill the cut: a Culture Enthusiast in Paris ranks 241 POIs and the first `religion` — weight 0.6, the lowest that archetype asks for — sat at rank **132**, where a three-day trip retrieves 72. Each category now keeps its own ranking and emits into a merged list at a rate set by its weight, so the head still belongs to what the traveller most wants while every category it wants gets roughly its share. And the keyword retriever had nothing to match on, for a reason that reads as a wording detail: the tokenizer does no stemming, and the query said "places of worship" where `worship` appears in 4 of 654 documents and `places` in 5, against `church` in 69. Together they take reachable `religion` POIs from 1 to 30 and **iconic coverage on a three-day trip from 20 of 24 to 24 of 24**, with retrieval quality unmoved on the project's own measures (recall@k 0.253 → 0.258, archetype precision 0.967 → 0.969). The cost is real and is the tail of the categories that were over-represented: `landmark` reachability falls from 39.7% to 19.8% and `museum` from 68.5% to 42.6%, for a net 417 → 403 POIs reachable overall. That is depth in three categories traded for breadth across all of them, and the iconic measure is what says the trade did not take the famous places with it. **Two of those categories were losing to a wording detail of their own** (issue #123). Applying #113's principle to every phrase rather than to `religion` alone found `landmarks` matching 2 of 654 documents against `landmark`'s 117, and `museums` 17 against `museum`'s 127 — invisible to BM25 for exactly the reason `religion` had been, and unnoticed because the graph carries both at 0.9 and 1.0 affinity so something always came back. Fixing them is not free, and that is the finding rather than a caveat on it: the pool is strictly zero-sum at a fixed `top_k`, and better phrasing alone takes `religion` straight back to 23 of the 30 it had just won. Phrasing and the graph's category quota (`build_graph.PREFERENCE_QUOTA_EXPONENT`) were therefore swept together (`evaluation/category_phrase_sweep.py`), at all three trip lengths — the configuration that looked clean at three days was quietly costing `religion` 8 POIs at five, and only two of the grid's configurations hold `religion` at or above today's value at every length. What ships takes reachable POIs on a three-day trip from **403 to 426**, `museum` from 42.6% to 52.8%, `landmark` from 19.8% to 23.3% and `religion` from 30 to 39, with iconic coverage still 24 of 24 and retrieval quality unmoved (recall@k 0.2578 → 0.2578, archetype precision 0.9693 unchanged). It still costs: `food`, `nature` and `shopping` each lose one reachable POI at three days, and the one-day pool falls 173 → 168 because a flatter quota spends 24 slots more evenly. **That last cost was then measured against the plan, and it is not one** (issue #143). The open question was whether one exponent can serve three pool sizes at all — flattening is free at 120 slots and expensive at 24 — so it was swept per trip length over 0.4–2.0, the range above 1.0 being the half #123 never tried (`evaluation/quota_topk_sweep.py`). The one-day pool does prefer a sharper exponent, as predicted: 168 at 0.5, 173 at 1.0, 174 at 1.2. But what that buys is a total rather than a spread — at 1.2 `history` falls 10 → 6, `food` 24 → 20 and iconic coverage 22 → 20, so a `top_k`-dependent exponent trades the categories the quota exists to protect for a headline number. And the headline does not reach anyone: over **84 plans** (2 cities × 7 archetypes × 3 trip lengths, both exponents, `evaluation/quota_plan_impact.py`) moving 0.5 to the Pareto-better 0.6 changes the aggregate stop count by **zero** — one-day trips differ on 2 of 14 and cancel, three-day on 1 of 14, five-day on 1 of 14. The three to five POIs this knob moves sit in the tail the router never selects, since a one-day plan takes eight stops from twenty-four candidates. So the exponent is a pool knob and not a plan knob, and #123's unmet criterion was written against a number the traveller does not see. It is left at 0.5: with the plan unmoved, changing it would be optimising a measure just shown not to carry. And `landmark` is still the catalogue's least reachable category at under a quarter — improved, not solved. And the diversity cap's own cost is stated in §3: at 4, about two-thirds of days carry four stops of one category. **Real routing no longer depends on anyone else's server.** This entry previously said `use_real_routing=True` stayed opt-in because it called a public, unauthenticated OSRM demo server with no uptime guarantee that rate-limited bursts. Issue #32 removed that dependency: the OpenStreetMap street network for each city is downloaded once at pipeline time (`pipeline/build_street_network.py`), pruned to what a distance query needs, and committed alongside a precomputed matrix over every point the router can be handed — the catalogue's POIs, the transport hubs, and the city centre each day is anchored at. At run time a real street distance is an array lookup, so it costs nothing per trip and works with the machine offline; a coordinate outside that catalogue is still solved against the committed street graph, and only a city we hold no network for falls back to the straight line. Measured against the OSRM server it replaces, over 868 walking pairs in Paris, the two agree to a mean 4.3% (median 2.1%) — while the haversine estimate both replace is 16.4% off that same reference. **The flag is on by default in the app since issue #94, and the comparability objection that kept it off did not survive being measured.** Its original reason — the OSRM demo server's uptime — went with issue #32; what remained was that every measurement here was taken with it off. Run `evaluation/comparative_analysis.py` both ways and the retrieval columns are bit-identical — recall@k, archetype precision and candidate counts, on all 61 queries × 3 configs — because retrieval does not know the flag exists. Only the two routing columns move, and they move the way replacing an estimate with a measurement should: km per stop on day 1 goes 0.697 → 0.912 for Fusion, 0.924 → 1.113 for Hybrid, 0.706 → 0.981 for standard prompting (+21% to +39%), while stops per day fall 2–4% as the real distances price days that were quietly overfull. The ranking between configs is unchanged on every column. The evaluations whose numbers *would* move — `toptw_measurement.py`, `toptw_scoring_ablation.py`, and now `comparative_analysis.py` — pass `use_real_routing=False` explicitly, so they keep the condition this report documents whatever the app defaults to, and `RouterAgent.run`'s own default stays False for the same reason. What is left is a traveller choosing between a distance measured on the street network and one that runs 16% short, at no cost per trip. **And the map now draws the route it measured.** It had always joined stops with straight lines whatever the mode said, so a Paris day the panel reported as 6.85 km was drawn as 3.17 — not a regression, but a contradiction issue #32 roughly doubled by moving distances onto the real network. Where a street network priced the day, the same graph supplies the path (`street_network.route_polylines`, one radius-limited Dijkstra per leg, ~0.3 s for a four-day trip), and the drawing lands within 0.4–9.1% of the day's own `distance_km` across both cities and all three street modes, against the ~50% shortfall before. Two things had to be right for that, and only one of them was the straight lines. `distance_km` also counts the journey from where the day *starts* — the city centre, or the arrival hub on day 1 — to its first stop, and that place is not in `route`, so it was drawn nowhere: on a Paris walking day it is 1.2–1.7 km, and a map tracing every street perfectly would still have come up 17–36% short without it. The day now carries its origin's coordinates and the map draws that leg too. Where no path exists the line is dashed and the caption says why, rather than a route being implied: transit keeps journey times and not the lines a journey used (RAPTOR's trip decomposition is not stored and the feeds' `shapes.txt` is never parsed), and with real routing off the straight line is the model itself. Drawing an actual transit route remains out of scope and unclaimed. **Day 1 now starts where the traveller lands.** Every day used to begin at the city centre, which is a reasonable proxy for a centrally booked hotel and a poor one for the day you arrive: the transfer in from the airport was not in the plan at all. The router takes an optional arrival gateway from `transport.csv` (`arrival_hub_id`, exposed as the sidebar's "Arriving at"), and the TOPTW model gives that gateway a node of its own that only day 1 starts from — later days are unchanged, because anchoring every day there would walk the traveller back out to the edge of town each morning. The effect is not decorative: a 3-day Paris trip arriving at Charles de Gaulle returns 8 stops and 26.2 km on day 1 where the same trip starting in the city returns 10 stops and 3.8 km. It is off by default ("Already in the city"), because the gateway cannot be guessed — assuming an airport would put a 23 km transfer at the start of a trip that arrives by train. **Public transport is modelled from the timetable, in both cities.** This entry previously read "there is still no transit-schedule modeling: `driving` and `hybrid` are private-car speeds". Stage 2 of issue #32 closed that: `optimization/raptor.py` implements RAPTOR (Delling, Pajor & Werneck, 2012) over the Île-de-France Mobilités and VBB GTFS feeds, and `data/street_network/PAR_transit.npz` and `BER_transit.npz` carry the resulting journey times between every catalogue point — the walk to the stop, the wait, the changes and the walk at the far end included.

  The plan was OpenTripPlanner, and the reason it was not used is worth recording because it is a claim about what the project needed rather than about OTP's quality. OTP2's transit router *is* RAPTOR; what OTP adds is a passenger-information API, which answers "how do I get from A to B". A distance matrix needs "how long from here to everywhere", and OTP2 no longer exposes that shape — one-to-many moved to the analysis projects, and the remaining sandbox travel-time endpoint returns isochrones and is documented as unsupported. Asked pairwise, Paris' 379 catalogue points are 143,641 queries; RAPTOR fills in every stop on the way to answering any one of them, so the whole matrix is 379 runs. Running the algorithm directly also kept the deployment story the previous section describes: no JVM, no second service, no compose file.

  Every origin is solved simultaneously — arrivals are an (origins × stops) array and each step of a route scan is one vectorised operation — and each pair is solved from thirteen departures between 08:00 and 20:00 with the **median** kept, because a single departure time bakes in whether the timetable happened to be kind. Access and transfer footpaths are real distances over the stage-1 walking network rather than straight lines. Every pair is also compared against simply walking and the faster is kept, so the matrix cannot propose a bus to cross a square.

  Measured: transit beats walking on 98% of Paris pairs by a median factor of 2.14 (average journey 23 minutes against 55 on foot) and on 95% of Berlin's by 1.98 (27 against 56). The effective door-to-door speed in a straight line is about 8 km/h — a figure that says more about waiting and walking than about how fast a metro moves. Spot checks against journeys with known answers hold (Gare de Lyon → Louvre 17 minutes, Eiffel Tower → Louvre 28, Charles de Gaulle → Notre-Dame 51, Brandenburg airport → Brandenburg Gate 45, Berlin Hauptbahnhof → Alexanderplatz 13 — the two airport figures unchanged by issue #92, which is what says that fix moved the *reason* for them rather than the answer), and four failure modes that produce plausible wrong answers rather than errors are pinned by tests: trips that overtake each other on one stop sequence (30 such patterns in the Paris feed), service written past midnight as `24:40:00`, a feed whose first three days precede its own publication and carry almost no service, and a place whose coordinate the street network cannot locate.

  That last one is a finding about the catalogue rather than the router, and it is the kind of error this project should expect more of. A place is routed from its coordinate, and some coordinates are the centroid of something large. Berlin Brandenburg's is the middle of the airfield; its nearest footway node is 1,225 m away in a field outside Waßmannsdorf. Access measured over the street network from there found two village bus stops and put the airport 240 minutes from the city on rural buses, while the airport's own platforms sat 785 m away in a straight line and were never considered. Nothing failed, and the number was wrong by a factor of five. Access is measured over the network only where the point sits within 150 m of it — which is 16,261 of Paris' 16,274 stops and 7,575 of Berlin's 7,581 — and by straight line with a detour factor otherwise, and platforms of one station are linked through the feed's own `parent_station`, because the walk from an S-Bahn platform to an airport express is inside a building no footway network describes.

  **That was a compensation, and issue #92 replaced it with a fix.** The straight-line fallback got the airport a defensible number, but from the wrong place: the row still said the traveller was standing between the runways, so every street distance, the snap offset added to every leg, and day 1's starting point were all measured from there. `build_transport.py` now moves each airport onto the passenger-facing point OSM records for it — its own station first, its nearest terminal second — and the three rows land 110–780 m from where they were. Brandenburg's footway offset falls from **1,225 m to 15 m**, Charles de Gaulle's from 185 m to 15 m, Orly's from 42 m to 26 m; all three are now inside the 150 m the transit build trusts, so Berlin's airport access stopped being estimated and started being measured, and Paris has no point left on the straight-line path at all (0 of 379, against 1 of 285 in Berlin — Spreepark, a park centroid, at 156 m).

  Two things are worth stating about it. **The preference order was decided by measurement, against what the issue specified.** #92 asked for terminal first and station second; built that way, CDG resolves to Terminal 2B, whose 800 m walking circle holds seven inter-terminal bus stops and no train — the RER B that makes the journey is further off than that — and CDG → Notre-Dame came out at 60 minutes against the hand-checked 51. Station first reproduces 51, and 55 to the Louvre, exactly. Terminals stay as the fallback, since not every airport tags a station of its own. **And the coordinate was only half of it.** Moving BER onto its terminal alone made the snap *worse*, 1,225 m to 1,865 m, because the committed Berlin walking network did not contain the airport at all: osmnx keeps only the largest connected component by default, `build_street_network.py` never overrode that, and at a 2 km margin the corridor linking the airport's 788 footway nodes to the city fell outside the box — so the airport's own paths were a second component and were dropped without a line of output. The margin is now 4 km (it reconnects at 3), the component decision is taken in one documented place, and a check compares each point's distance to the whole download against its distance to what survives pruning: at the old margin it reports “Berlin Brandenburg Airport 15 m → 1,818 m” and refuses to write the file.

  **What is still missing.** The matrix is one representative weekday, so it cannot answer "what about Sunday", and it is a median rather than a departure-time function, because the TOPTW model consumes one duration matrix per trip and cannot express a cost that changes with the clock. And GTFS goes stale quickly: the feed used here covers about a month, so this is a file that needs re-running, not a one-time build.

  One simplification carries over from stage 1: for the street modes, a real *distance* is measured per leg, but what a kilometre costs in minutes is still the mode's single calibrated speed rather than a per-street limit. That is deliberate — `driving`'s 25km/h is door-to-door urban driving in a historic centre, and OSM's posted limits describe an empty road — but it means those duration matrices are a function of the distance matrix rather than an independent measurement. Transit is the exception: its minutes are solved, not derived.

## 6. How this maps to "done"

Every proposal deliverable has working, tested code behind it in this repository today: a knowledge graph, a Fusion RAG pipeline with a genuine RRF fusion of three independent retrieval signals, a multi-agent orchestrator that calls real forecasting/clustering/optimization tools rather than asking an LLM to hallucinate them, a comparative-analysis harness with saved, reproducible results, and an interactive Streamlit prototype — verified running in a browser, not just imported without error. The honest gaps are documented above rather than glossed over, and each one names the specific file where a real-data or real-LLM swap would plug in.
